# Rust core for the desktop restart

[open-sesame-core](core/src/lib.rs) is the headless core of the Tauri restart in [epic #58](https://github.com/OpenCoven/open-sesame/issues/58). It is not shipped: the Swift host and Python bridge under [desktop](../desktop/AGENTS.md) remain the running application until the cutover. Read the root [instructions](../AGENTS.md) and the [repository map](../docs/repository-map.md) first; the ownership, evidence, publication and prose rules there apply here.

Keep the core free of any Tauri dependency so `cargo test -p open-sesame-core` runs without a window on macOS, Windows and Linux. The application member is [src-tauri](../src-tauri/src/lib.rs), with its own [instructions](../src-tauri/AGENTS.md); it depends on the core, never the reverse. The embedded Coven engine under `desktop/engine` is a separate Cargo project that the root workspace excludes, with its own lockfile.

[protocol.rs](core/src/protocol.rs) is the wire contract that [bridge.js](../dist/bridge.js) already speaks: `{requestId, method, params}` requests, `{requestId, result}` or `{requestId, error}` replies, and events with an `event` key. Do not rename fields or change reply shapes without changing the UI transport in the same reviewed change.

[gate.rs](core/src/gate.rs) decides whether a request may run before any feature code does, in the fixed order documented at the top of that file. Local features run signed out; only methods listed as account-backed need a session, as decided in [#60](https://github.com/OpenCoven/open-sesame/issues/60). Admit a method by adding it to `PORTED` in the change that ports its handler, and remove any not-ported entry that would still match it. Do not admit a feature ahead of the issue that ports it, weaken the main-window rule, or let a handler run before the gate. Add account-backed or per-system entries to their lists, not as special cases in handlers.

[handler.rs](core/src/handler.rs) is where an allowed request goes when it needs no window: `Core::handle` answers the methods a core module claims and gives every other method the unknown-method reply, so a method listed in the gate ahead of its handler never reaches feature code. [system.rs](core/src/system.rs) answers `system.info` with the field names of the Python bridge. `Core::shutdown` is the one place that stops what the core owns; the application calls it on every exit.
[storage](core/src/storage/mod.rs) is the one SQLite database, opened in the directory the host passes in; the core never works out a data directory itself. The UI reaches it only through the typed commands in [commands.rs](core/src/storage/commands.rs): do not add a command that takes SQL, a table name or a column name, and keep every statement a fixed string with bound parameters. Every row keeps a stable ID and an `updated_at` the core sets and every write moves forward. No save to items, projects or saved articles replaces a row blindly: the core assigns IDs as UUID v7, a create may instead carry a UUID v4 the UI chose so that the same create sent again after a lost reply saves one row, and an edit sends the `updatedAt` it started from as `expectedUpdatedAt`. A save that does not name the row's current `updatedAt` is refused with a conflict, changing nothing, unless it would change nothing. Give any new table that the UI or an agent edits the same rules. A write returns only after its transaction commits, and a failure is returned as an error, never as a saved result. Change the schema only by appending a migration in [schema.rs](core/src/storage/schema.rs); never edit one that exists. No token, password or other credential is stored here, and nothing is migrated from the old `localStorage` keys.
[process](core/src/process/mod.rs) is the one way the core runs an installed command-line tool; terminals are separate and described below. `run` starts the program directly, never through a shell, always with a timeout and an output cap, and kills the whole process tree on every exit path: a new session and process group on Unix ([unix.rs](core/src/process/unix.rs)), a kill-on-close job object on Windows ([windows.rs](core/src/process/windows.rs)). Do not log arguments, output or environment values, and do not weaken the tree kill or a time limit to make a test pass. [env.rs](core/src/process/env.rs) captures the login-shell environment once at startup and falls back to the inherited environment; call it off the main thread, because a user's startup files can take seconds. [find.rs](core/src/process/find.rs) resolves a tool from the user's own path for it, then `PATH`, then known install locations, and never searches the working directory. The tests use the Rust [fixture](core/src/bin/fixture_cli.rs), not Python or a real provider CLI, and must leave no fixture process behind.
[auth](core/src/auth/mod.rs) is the sign-in logic of `desktop/Authentication.swift` without a browser, a keychain or a network stack: PKCE, the callback rules in [callback.rs](core/src/auth/callback.rs), access-token verification in [token.rs](core/src/auth/token.rs) and the state machine in [controller.rs](core/src/auth/controller.rs). The host supplies the HTTP client, the credential store and the signed-out marker through the traits in [api.rs](core/src/auth/api.rs) and [store.rs](core/src/auth/store.rs); that wiring is [#72](https://github.com/OpenCoven/open-sesame/issues/72). Keep these rules: only the public client ID ships; a session exists only after the token's signature and subject are verified; only the refresh token is saved, and only through the store; no token appears in a log, an error, debug output or the status the UI reads. Tests use fakes and an RSA key generated for the run, never a real account; `rsa` and `rand` are test-only dependencies and must not move into the shipped code. Check a changed request path or body against the vendored SDK source in `vendor-src/workos-ios` first.

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root, then `npm run check`. [check-core-gate.mjs](../scripts/check-core-gate.mjs) reads the gate lists as text and fails when the authored UI names a bridge method the gate does not classify; keep the lists as plain string literals. A passing local run is evidence for the operating system it ran on only; three-system and hosted results are recorded separately.

[terminal](core/src/terminal/mod.rs) runs interactive shells for panes ([#74](https://github.com/OpenCoven/open-sesame/issues/74)). It is the only place the core starts a program through a shell, and the only arguments it builds are the fixed launcher forms in [launch.rs](core/src/terminal/launch.rs): the default shell, one `coven` task, one Bash command, or `ssh -tt user@host` with a quoted remote command. Validation sentences and limits are the Python bridge's, so the page shows the same text. [session.rs](core/src/terminal/session.rs) owns the pseudo-terminal through `portable-pty` and three threads per pane: one reads and stops at `HIGH_WATER` unacknowledged bytes, one batches and sends, and one types queued input so a request never waits for a program that is not reading. On macOS input is typed a line at a time with a short pause, because input waiting in the terminal driver while a line-editing shell switches modes comes out damaged; the measurements are beside `Pace` in that file, and the pause is a measured setting, not a guarantee. Output is handed to a sink as bytes, then exactly one `Exit`; the core knows nothing about Tauri. Because `portable-pty` does the spawn, the process runner's spawn-time tree setup cannot be reused: [tree.rs](core/src/terminal/tree.rs) signals every process in the shell's session on Unix and assigns a kill-on-close job object right after spawn on Windows. `Core::shutdown` closes every pane. A process that leaves the session on Unix, or the application being killed without its exit event, is outside what this can end; say so when recording evidence. The tests in [terminal.rs](core/tests/terminal.rs) use real shells and count processes afterwards; keep them real.
