# Rust core for the desktop restart

[open-sesame-core](core/src/lib.rs) is the headless core of the Tauri restart in [epic #58](https://github.com/OpenCoven/open-sesame/issues/58). It is not shipped: the Swift host and Python bridge under [desktop](../desktop/AGENTS.md) remain the running application until the cutover. Read the root [instructions](../AGENTS.md) and the [repository map](../docs/repository-map.md) first; the ownership, evidence, publication and prose rules there apply here.

Keep the core free of any Tauri dependency so `cargo test -p open-sesame-core` runs without a window on macOS, Windows and Linux. The application member is [src-tauri](../src-tauri/src/lib.rs), with its own [instructions](../src-tauri/AGENTS.md); it depends on the core, never the reverse. The embedded Coven engine under `desktop/engine` is a separate Cargo project that the root workspace excludes, with its own lockfile.

[protocol.rs](core/src/protocol.rs) is the wire contract that [bridge.js](../dist/bridge.js) already speaks: `{requestId, method, params}` requests, `{requestId, result}` or `{requestId, error}` replies, and events with an `event` key. Do not rename fields or change reply shapes without changing the UI transport in the same reviewed change.

[gate.rs](core/src/gate.rs) decides whether a request may run before any feature code does, in the fixed order documented at the top of that file. Local features run signed out; only methods listed as account-backed need a session, as decided in [#60](https://github.com/OpenCoven/open-sesame/issues/60). Admit a method by adding it to `PORTED` in the change that ports its handler, and remove any not-ported entry that would still match it. Do not admit a feature ahead of the issue that ports it, weaken the main-window rule, or let a handler run before the gate. Add account-backed or per-system entries to their lists, not as special cases in handlers.

[handler.rs](core/src/handler.rs) is where an allowed request goes when it needs no window: `Core::handle` answers the methods a core module claims and gives every other method the unknown-method reply, so a method listed in the gate ahead of its handler never reaches feature code. [system.rs](core/src/system.rs) answers `system.info` with the field names of the Python bridge. `Core::shutdown` is the one place that stops what the core owns; the application calls it on every exit.
[storage](core/src/storage/mod.rs) is the one SQLite database, opened in the directory the host passes in; the core never works out a data directory itself. The UI reaches it only through the typed commands in [commands.rs](core/src/storage/commands.rs): do not add a command that takes SQL, a table name or a column name, and keep every statement a fixed string with bound parameters. Every row keeps a stable ID and an `updated_at` the core sets and every write moves forward. No save to items, projects or saved articles replaces a row blindly: the core assigns IDs as UUID v7, a create may instead carry a UUID v4 the UI chose so that the same create sent again after a lost reply saves one row, and an edit sends the `updatedAt` it started from as `expectedUpdatedAt`. A save that does not name the row's current `updatedAt` is refused with a conflict, changing nothing, unless it would change nothing. Give any new table that the UI or an agent edits the same rules. A write returns only after its transaction commits, and a failure is returned as an error, never as a saved result. Change the schema only by appending a migration in [schema.rs](core/src/storage/schema.rs); never edit one that exists. No token, password or other credential is stored here, and nothing is migrated from the old `localStorage` keys.
[process](core/src/process/mod.rs) is the one way the core runs an installed command-line tool; terminals are separate and described below. `run` starts the program directly, never through a shell, always with a timeout and an output cap, and kills the whole process tree on every exit path: a new session and process group on Unix ([unix.rs](core/src/process/unix.rs)), a kill-on-close job object on Windows ([windows.rs](core/src/process/windows.rs)). Do not log arguments, output or environment values, and do not weaken the tree kill or a time limit to make a test pass. [env.rs](core/src/process/env.rs) captures the login-shell environment once at startup and falls back to the inherited environment; call it off the main thread, because a user's startup files can take seconds. [find.rs](core/src/process/find.rs) resolves a tool from the user's own path for it, then `PATH`, then known install locations, and never searches the working directory. The tests use the Rust [fixture](core/src/bin/fixture_cli.rs), not Python or a real provider CLI, and must leave no fixture process behind. The limits found in the review of the runner are tracked in [#97](https://github.com/OpenCoven/open-sesame/issues/97); these rules came out of it. The capture reads the environment from a pipe of its own on Unix (`Report` in [unix.rs](core/src/process/unix.rs)), because the standard output is shared with whatever the user's startup files leave running; the two markers on standard output only say that the shell reached the command and finished it, and the environment between them is the fallback for a system that gives no such pipe. The shell is handed the pipe under descriptor 100 or above (20 or above when the process may open 100 files or fewer, and no pipe at all at 20 or fewer, which no test covers) and the command appends to it: the bash that macOS ships closes descriptors 3 to 19 when it starts as an interactive login shell, and that same bash, as `bash` and as `sh`, refuses a plain `>` to the pipe when `noclobber` is set. So do not lower the number without running the background-output test, and do not change the redirection without running the `noclobber` test beside it, both on macOS, where that bash is; they run under zsh, bash and sh there, and under fish too on Linux except for the `noclobber` case, which leaves fish out; ksh is not in them, and dash only where it is `sh`, as on Ubuntu. Everything the startup files start inherits that descriptor, so the reading ends when the shell has exited and the pipe is read empty, not when the pipe closes. The shell's ordinary output is another matter: the runner's rule for output still applies after the shell has exited, which is up to a quarter of a second for something inside the process group that holds it, and longer for something outside the group (`DRAIN` in [mod.rs](core/src/process/mod.rs)). Under zsh on a busy machine a startup line of the form `cmd >/dev/null 2>&1 &` can cost a capture that quarter of a second, because zsh lowers the job's priority before the job has redirected and the shell can exit while the job still holds its output (seen on a Mac under load by a reviewer; the result is still right, and nothing is changed for it). A captured variable whose name or value is not valid UTF-8 is left out of the result, as `ShellEnv::inherited` leaves such variables out, and is never passed on with replacement characters; since the result is the shell's own environment and not the launch one with changes laid over it, a value the application was launched with under that name is gone too. Of a `PATH` that is not valid UTF-8 the directories that are valid are kept, and one with no valid directory is left out, which gives the capture up. A helper thread that cannot be started makes `run` return `RunError::Io` with the tree already killed; start such threads through `start` in [mod.rs](core/src/process/mod.rs), never with `std::thread::spawn`, which panics. The runner assumes it is the only code that collects its children: the application must not ignore `SIGCHLD`, and no thread may wait for any child (`waitpid(-1, …)` or the like), or `exited` never sees the exit and a reused process-group number could be signalled. Still open in #97 and not fixed: after the kill `retire` waits for the child without a limit, so `run` does not return while a program this user cannot kill keeps running, and on Unix nothing ends running children when the application itself is killed. The login-shell tests note a shell that is not installed and pass without running, except those that came with #105, which name their shell outright (`/bin/sh`, `/bin/bash`, and `/bin/zsh` in a test that runs on macOS only) and fail without it; CI names the shells each system must have in `OPEN_SESAME_REQUIRE_SHELLS`, a shell is matched there by its file name, and a missing one then fails the run, so do not remove a shell from that list to make a job pass.
[auth](core/src/auth/mod.rs) is the sign-in logic of `desktop/Authentication.swift` without a browser, a keychain or a network stack: PKCE, the callback rules in [callback.rs](core/src/auth/callback.rs), access-token verification in [token.rs](core/src/auth/token.rs) and the state machine in [controller.rs](core/src/auth/controller.rs). The host supplies the HTTP client, the credential store and the signed-out marker through the traits in [api.rs](core/src/auth/api.rs) and [store.rs](core/src/auth/store.rs); that wiring is [#72](https://github.com/OpenCoven/open-sesame/issues/72). Keep these rules: only the public client ID ships; a session exists only after the token's signature and subject are verified; only the refresh token is saved, and only through the store; no token appears in a log, an error, debug output or the status the UI reads. Tests use fakes and an RSA key generated for the run, never a real account; `rsa` and `rand` are test-only dependencies and must not move into the shipped code. Check a changed request path or body against the vendored SDK source in `vendor-src/workos-ios` first. The credential store can wait for a person: a locked keyring shows its unlock prompt and answers when the prompt does, or never ([#130](https://github.com/OpenCoven/open-sesame/issues/130)). So nothing else may wait with it. `authenticated` and `status` answer from a copy of the state and never take the state's lock, which is why the gate keeps answering while a save or a delete is out. Every store call a caller waits for runs on a thread of its own through `AuthController::store` or `remove` and is waited for no longer than `STORE_LIMIT` (two minutes); after `STORE_SOON` (two seconds) the status says the keychain is being waited for. A call given up is not ended, because nothing can end it: its thread stays until the store answers, what it was asked to do may still happen then, and until it returns every store call fails at once instead of waiting behind it and `begin_sign_in` answers `StoreBusy`, because a new sign-in could not be saved. `store_given_up` says so to the host, and `store_waited_for` says whether a call is being waited for past the first two seconds, which is when the status reads that the keychain is being waited for; the host refuses Sign in on either without looking at the store. A removal asked for meanwhile, by Sign out or for a session the server ended, is owed: it is made on that call's thread when the last such call returns and before any other store call is let through, so that a save given up before a sign-out does not land after it and stay. That removal, made in `returned`, is the one store call with no limit and nobody waiting: while it waits nothing else is let through, its outcome changes no status and announces no change, so the status goes on saying the credential could not be removed after it has been, and a removal that fails then says nothing. What it removes is whatever is saved when the call returns, which can be a later sign-in whose save was the call given up; that sign-in was reported as not saved. If the call never returns the removal is never made. After a Sign out the signed-out marker is then what keeps the next launch from restoring, for as long as the host keeps the marker, and the release host keeps it in memory only ([#105](https://github.com/OpenCoven/open-sesame/issues/105)); for a session the server ended no marker is set. A call that panics after it was given up counts as returned. Sign out publishes the signed-out state and then tells its caller that it has begun, with the address that ends the remote session, before it asks the store (`sign_out_now`). The three things a person can ask for while a write is waited for have forms that answer `AuthError::StoreBusy` instead of waiting: `begin_sign_in`, `cancel_now` and `sign_out_now`; a request from the page uses those, and the plain `cancel` and `sign_out` are for code that may wait. Both numbers are proposals in the pull request for #130 and the owner's to change. Do not call the store anywhere but through `store` and `remove`, and do not read the state's lock for the gate.

Refresh recovery follows the [recovery contract](../docs/auth-refresh-recovery.md): save a returned replacement before JWKS verification, retry saving or verification without replaying the consumed credential, and keep credential lineage separate from session cancellation. `AuthController::shutdown` now closes admission and drains a running refresh; call it from the exit thread, never from a network or change callback. Only signature and subject verification can open a session. The [refresh tests](core/src/auth/tests/refresh.rs) cover these boundaries without a real account.

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root, then `npm run check`. [check-core-gate.mjs](../scripts/check-core-gate.mjs) reads the gate lists as text and fails when the authored UI names a bridge method the gate does not classify; keep the lists as plain string literals. A passing local run is evidence for the operating system it ran on only; three-system and hosted results are recorded separately.

[terminal](core/src/terminal/mod.rs) runs interactive shells for panes ([#74](https://github.com/OpenCoven/open-sesame/issues/74)). It is the only place the core starts a program through a shell, and the only arguments it builds are the fixed launcher forms in [launch.rs](core/src/terminal/launch.rs): the default shell, one `coven` task, one Bash command, or `ssh -tt user@host` with a quoted remote command. Validation sentences and limits are the Python bridge's, so the page shows the same text. [session.rs](core/src/terminal/session.rs) owns the pseudo-terminal through `portable-pty` and three threads per pane: one reads and stops at `HIGH_WATER` unacknowledged bytes, one batches and sends, and one types queued input so a request never waits for a program that is not reading. On macOS input is typed a line at a time with a short pause, because input waiting in the terminal driver while a line-editing shell switches modes comes out damaged; the measurements are beside `Pace` in that file, and the pause is a measured setting, not a guarantee. Output is handed to a sink as bytes, then exactly one `Exit`; the core knows nothing about Tauri. A pane ends when its shell exits, whatever the shell leaves running ([#112](https://github.com/OpenCoven/open-sesame/issues/112)): macOS ends the read by itself, Windows has the `watch` thread in `session.rs`, and on other Unix systems the reader waits for output in short steps and looks at the shell between them, as [exit.rs](core/src/terminal/exit.rs) describes; there a job that keeps writing delays the end by about a third of a second (the shell is looked at every 50 ms, and the reader then waits a quarter of a second in all for output; 0.30 to 0.44 s was measured), or until a megabyte has been read after the exit was noticed, whichever comes first. The exception on every system is a pane whose output the page has stopped acknowledging: it stays open at the high-water mark whether or not its shell has exited. Opening a pseudo-terminal is tried up to four times within about 75 ms, because macOS now and then refuses one with an error number of its kernel's own that means "try again"; the reasons are beside `OPEN_PAUSES` in `session.rs`. The end of a pane kills everything still in the shell's session on every system, a job started with `nohup` included; whether such a job should be left running instead is an open owner decision in #112, so do not change that kill in passing. Two requests for one pane ID never leave a shell the list cannot reach: `terminal.close` takes only the pane it closed off the list, and `terminal.open` closes a pane it displaces. Because `portable-pty` does the spawn, the process runner's spawn-time tree setup cannot be reused: [tree.rs](core/src/terminal/tree.rs) signals every process in the shell's session on Unix and assigns a kill-on-close job object right after spawn on Windows. On Windows it also clears this process's "ignore Control+C" attribute before the first shell starts, because a shell inherits it and then never sees the Control+C a pane types; do not remove that call without a Windows run of `control_c_interrupts_the_running_command` started the way CI starts it. On Windows a close, and a start whose shell cannot be taken over, wait for the shell's process to end and give a killed shell five seconds; past that the caller goes on with the shell possibly still there (a close reports the pane ended, a failed start answers that the shell could not be started), and the pane's other processes are never waited for. The pseudo-console is closed after that wait, and on builds before Windows 11 24H2 that close may itself wait (from Microsoft's page for `ClosePseudoConsole`; not produced in any test); `ENDING` in [tree.rs](core/src/terminal/tree.rs) says when. `close_all_detached` is for the application's window thread, when a page that starts to load has replaced the page whose panes these were; Quit still waits for those panes through `close_all`. `Core::shutdown` closes every pane and the terminals refuse every later `terminal.open`, because the application opens panes on them directly and not through `Core::handle`. A process that leaves the session on Unix, or the application being killed without its exit event, is outside what this can end; say so when recording evidence. The tests in [terminal.rs](core/tests/terminal.rs) use real shells and count processes afterwards; keep them real.

The startup environment is the login shell's effective environment, including variables its profile unsets, with only shell-private values restored from inheritance. NUL-separated capture retains valid Unicode OS environment names. Discovery requires the caller's effective execute access, uses a finite list including standard Cargo/Bun locations after PATH, and honors absolute configured install roots. `Core::find_tool` reads the current stored per-tool override before searching the host-supplied environment; a failed storage read or bad explicit override must not silently select a different executable. [Runtime regressions](core/tests/runtime.rs) cover storage ownership, shutdown, failure and discovery wiring.
