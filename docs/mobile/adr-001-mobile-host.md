# ADR 001: iOS and iPadOS host for the shared workspace

Status: **Proposed; not ratified.** Selected recommendation: a thin Swift iOS/iPadOS application hosting the existing authored web UI in WKWebView, with explicit native storage/authentication boundaries. This is a decision-ready proposal for [#35](https://github.com/OpenCoven/open-sesame/issues/35), under [#33](https://github.com/OpenCoven/open-sesame/issues/33), not approval to implement a transport, change WorkOS settings or ship an app. Val's explicit approval of an exact revision, scope and conditions is still required. No approval is inferred from this document, issue assignment, PR review automation or merge.

Source baseline: Open Sesame `a5002e03675e708382f9ae2ca7b531beff8d576a`. The [inventory](source-inventory.md) records the related repository revisions and examined owners. [#34](https://github.com/OpenCoven/open-sesame/issues/34) remains an open dependency: architecture work can be reviewed now, but reference parity and final ratification must be reconciled with its delivered artifact. All mobile behavior below is a requirement for future implementation, unless identified as an existing source fact.

## Decision and platform floor

Recommend iOS 18.0 and iPadOS 18.0 as the first deployment minimums, with iPhone and iPad targets in one application. This is a proposed support floor, not a WebKit minimum or proof that the current Mac target compiles for iOS. It aligns the initial qualification floor with [Chat's existing companion target](https://github.com/OpenCoven/chat/blob/f34022acc3dfeb55634d5c8132ed41a02181a534/apps/ios/ChatCompanion/project.yml), limits the initial OS/device matrix, and leaves older devices unsupported until separately evaluated. The vendored [WorkOS source pin](../../vendor-src/workos-ios/README.md) declares iOS 16 in its archived `Package.swift`; authentication therefore does not itself require raising this proposal above 18. Pin the actual Xcode/SDK/compiler and dependency versions in #38's reproducible build; the desktop Swift 6.2+ build does not establish that mobile build.

Use a small UIKit scene/container, with SwiftUI only where it simplifies native presentation, and WKWebView for Today, Projects, Widgets, Focus and Console. Reuse authored `dist/` models, validation and presentation owners; #36 adapts layout after #34 delivers the reference. The shell supplies lifecycle, safe-area/keyboard geometry, native dialogs, protected credentials and a narrowly allowlisted bridge. It does not port AppKit panels, the Python PTY service or embedded CLI execution onto a phone. Native storage is a persistence implementation beneath existing models, not a second workspace model.

Android is a later host decision, with no chosen minimum API level or supported package yet. Preserve platform-neutral model and capability contracts so Android can implement them later. Responsive CSS, a WebView on another platform or Linux portable checks do not qualify Android. Revisit this ADR before selecting its host/toolchain and security boundary.

## Packaging and renderer boundary

Bundle reviewed authored web assets, fonts and their licenses for offline loading. Use [WKWebView's restricted local-file load](https://developer.apple.com/documentation/webkit/wkwebview/loadfileurl(_:allowingreadaccessto:)) with read access limited to that asset directory; never grant the data container, home directory or arbitrary downloads as web roots. Preserve script order, content hashes, sanitization and widget lifecycle. Remote provider pages belong in the system browser or a separate unprivileged web surface, never in the bridge-bearing main document. Block unexpected navigation and subframe/native-method calls at the receiver, even when a caller sets a native flag.

New mobile receiver code must check the exact owned WKWebView, main frame, resolved bundle origin, session state, method, parameters and operation authority on every request. A fixed local origin is an asset boundary, not authentication. Do not enable the dormant development WebSocket path, expose Python stdio over a socket, reuse a generic RPC proxy or forward arbitrary CLI arguments. The current [Mac receiver](../../desktop/OpenSesame.swift), [renderer bridge](../../dist/bridge.js) and [sign-in-only HTTP preview](../../desktop/dev_server.py) remain unchanged by this ADR.

Package one self-contained reviewed application, without downloaded executable plugins or a remote replacement for bundled UI. Declarative tools remain data under the existing validator and declared operations; mobile availability must narrow their executable operations, never expand them. Assess actual tool/plugin behavior against Apple's [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), especially 2.5.2, 2.5.6 and minimum functionality, before store preparation; this proposal promises no store acceptance. Signing identities, entitlements, distribution, privacy declarations and submission remain #45 gates and require separate authority.

## Data, account and offline behavior

Reuse app item/project IDs and relationships, legacy key migration, drafts, installed widget state and tool instance schema. #37 must introduce durable mobile persistence through the existing owners, with versioned migration, atomic acknowledged writes, bounded recovery/export and explicit errors. Boot must hydrate before any renderer default writes; save success follows durable acknowledgement. Never copy the reference's demo localStorage as production state or introduce an independent Today/Focus/familiar database. Browser localStorage alone is not accepted as the mobile durability contract.

Choose a persistent WK website data store and stable application identity; keep account credentials and pairing keys in native protected storage outside JavaScript. AuthKit login and device pairing remain separate domains. Reuse the existing WorkOS public-client PKCE, verified session/user binding, expiry, cancellation epoch and sign-out contract; adapt presentation to iOS rather than import AppKit. #38 must prove callback routing, refresh/expiry and Keychain behavior for the mobile app. Existing production callback registrations are not presumed valid for a new bundle, and this ADR changes none of them. No API secret or credential may enter the bundle, renderer, URLs or logs. See [the current account contract](../workos-login.md).

For the proposed first milestone, verified account state unlocks the workspace. An already unlocked installation may continue local work offline only while its verified session is unexpired; a fresh install or expired session presents sign-in/recovery and preserves saved data without granting access through a renderer flag. No offline grace token or entitlement is invented. Transient refresh failure must not destroy data or falsely mark a companion connected. Changing this product policy requires explicit review in #38. This is consistent with the existing Mac account gate while keeping local data operations independent of companion reachability.

While unlocked, Today/Projects, saved local widgets and Focus operate without a companion or network. Account sync is not implied: import/export or future sync must preserve canonical models and obtain separate review. Fresh provider reads, familiar execution and desktop operations remain disconnected/unavailable, with saved content clearly marked when stale. Logout locks account-gated content, retires pending operations/approvals and clears relevant live credentials; it does not erase the workspace. Forgetting a companion revokes/deletes its local credential according to the selected protocol without silently enrolling again or wiping local notes.

## Lifecycle and accessibility

Treat background suspension, scene disconnection, WebKit content-process termination and device restart as normal recovery paths. Flush acknowledged mutations and retain unsaved drafts on each edit, with lifecycle checkpointing as a supplement; a final background callback is not the only durability mechanism. Retire polling/event subscriptions and pending approval UI when the scene loses authority. On foreground or [web-process termination](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webviewwebcontentprocessdidterminate(_:)), restore the same IDs/drafts, revalidate account and transport/grant state, then reconcile canonical run/history receipts before allowing another send. An interrupted request is uncertain, not permission to retry automatically. A companion run may continue on its authoritative host; the phone's disappearance is neither proof of cancellation nor success.

Focus #41 must persist start/deadline/pause state and recompute from elapsed time after suspension or clock changes instead of relying on JavaScript interval ticks. [Apple background execution](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app) is scheduled/limited; this app promises no always-running timer, background agent socket or guaranteed background completion alert. Notifications, push and background modes require their own reviewed behavior and permissions. Multiple iPad scenes need either one documented writable workspace owner or revision-aware coordination before enabling simultaneous edits.

WKWebView does not prove accessible interaction. #36/#44 must retain semantic controls, names, focus order and selected/expanded states; reconcile native and web modal focus, external-keyboard traversal/Escape, safe areas and software-keyboard occlusion. Qualify text scaling/reflow, readable contrast, Reduce Motion, touch targets and VoiceOver on an actual iPhone and iPad, including long lists/chat and portrait/landscape/split view. Compare with [Apple's accessibility guidance](https://developer.apple.com/documentation/uikit/accessibility-for-uikit). Missing assets or fonts must preserve readable controls; no success state depends on color, hover or animation alone.
