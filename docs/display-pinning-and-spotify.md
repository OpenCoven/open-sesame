# Display placement and shared Spotify configuration

Use the visible monitor control in the activity rail or application header, or open Widget options → Display and choose Pin to the monitor you want. The same choices are available in the menu-bar icon's Widget display submenu, including while the widget is closed. Choose Follow pointer to restore automatic following. Keep open controls docked outside dismissal; in the pop-out application it becomes Keep on top. Display pinning independently selects a monitor for the notch, launcher and detached application. An unpinned detached application moves freely; choosing a display moves its existing window into that screen’s usable bounds, retaining independent width and height.

The native host stores the selected monitor's [ColorSync display UUID](https://developer.apple.com/documentation/colorsync/cgdisplaycreateuuidfromdisplayid(_:)) in local preferences, with its display name. It resolves that hardware identity against the current screen list instead of persisting a transient screen number or array position. A valid pin takes priority over the pointer. If the screen is unavailable the widget safely follows the pointer and retains its preference; it returns to the pinned screen after reconnection. The widget menu labels the unavailable preference. Menu tracking, dragging and native dialogs defer automatic motion, and screen changes continue to recalculate native geometry. Hardware identifiers stay native and are not sent to the page or a provider.

Open Sesame now includes its owner-supplied public Spotify client ID in the native host and public web configuration. Users choose Connect → Continue with Spotify; they do not need to register a developer application or supply their own client ID. Existing valid explicit overrides are retained. PKCE still generates per-attempt verifier/state and validates the exact callback, and tokens remain in native session memory. No client secret is bundled. Spotify's [PKCE guide](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) describes this public-client flow, and its [app guide](https://developer.spotify.com/documentation/web-api/concepts/apps) covers custom native callback schemes.

The native callback remains `opensesame-spotify://auth/callback`. A read-only initial authorization preflight with the provided public client reached Spotify's login service without an invalid-client or invalid-redirect response; no account was signed in and no token was obtained. Actual account access, consent and playback remain provider acceptance steps. The embedded player's own sign-in is separate from the app's basic profile connection. Website operators must register their actual HTTPS callback; this registration is an app-maintainer task rather than a per-user setup step.

Native regression checks exercise pin priority, temporary unavailability, ordering changes, persisted UUID restoration, invalid preference fallback and return to pointer following. Renderer tests exercise native-only controls and selected/unavailable/detached labels. Spotify tests check default selection, preserved overrides, PKCE and strict callback rejection. They do not move a physical window, select a real monitor preference, sign in or capture audio/screens. Device acceptance must confirm the menu choice, actual cross-display placement, restart/reconnection behavior and a real Spotify return in the installed build.

## Spotify account library

After connecting in Media → Music → Spotify, Your library loads the account’s Liked Songs automatically. Choose Playlists to browse owned and followed playlists, including private and collaborative lists. Load more fetches the next page; selecting a song or playlist opens it in the existing Spotify player. Refresh retries a failed read. Empty libraries and provider failures have separate messages.

Reconnect existing Spotify sessions to grant the read-only `user-library-read`, `playlist-read-private` and `playlist-read-collaborative` scopes alongside profile access. Native tokens remain inside the Mac host; only normalized library items reach the widget. Library data stays in memory and is retired on disconnect, account change, expiry or widget deactivation. Spotify’s embedded playback session remains separate from account library access. Synthetic checks do not establish live account or installed playback acceptance.
