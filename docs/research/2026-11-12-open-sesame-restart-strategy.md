# Rebuild Open Sesame around agent attention

The best restart is a smaller product, not a faithful port: a summonable, local-first panel for people who run command-line coding agents, showing which agent or task needs them, giving them real terminals and quick capture, and built as a clean framework-free shell on Tauri 2 into which features are admitted one at a time. The evidence points there from three directions. The current code spans about 25 feature areas, loads all 114 scripts at startup whatever is "installed", and by the project's own capability matrix has almost nothing accepted on a real device. The model labs' desktop apps now cover command-centre features on all three operating systems, but each runs only its own agent, while independent orchestrators keep failing commercially (Conductor was acquired and is being wound down this month; Vibe Kanban shut down in April). Three positions remain thinly occupied: multi-vendor agent sessions with a GUI on Windows and Linux, agent-status and approval surfaces outside macOS, and personal widgets combined with agent sessions and real terminals in one local app. Four parts of the written Tauri plan conflict with the research and should change before any code is written: the sign-in gate on every method, terminal output as base64 events, a window that quits on close with no global shortcut, and reliance on the window label as a security boundary; a fifth, keeping `dist/` unchanged, preserves the structure that caused the project's recurring regressions. Local models belong in the app as an optional endpoint and later as local transcription, never as the default agent brain; harness integration should go terminals first, an MCP server second, ACP third, always by launching the user's own unmodified CLI and never touching a credential; computer use should stay out of the restart. The main caveats are that nobody has measured demand for the combined product, the researchers never ran the app, and several vendor policies are ambiguous.

*How to read this report: statements followed by a link are evidence gathered by the researchers. "Researchers' inference" marks a conclusion the researchers drew from that evidence. "Judgment" marks this report's own reasoning. Facts about the Tauri design and plan come from reading `docs/superpowers/specs/2026-11-12-tauri-cross-platform-design.md` and `docs/superpowers/plans/2026-11-12-tauri-cross-platform.md` in the local clone; neither file was modified.*

## The current app spans 25 feature areas and almost none is accepted on a real device

Open Sesame describes itself as a local widget workspace for notes, tasks, bookmarks, focus, reading, media and terminals that lives in the Mac notch or menu bar ([README](https://github.com/OpenCoven/open-sesame/blob/main/README.md)). The shipped page still carries prototype branding, including a "Private prototype" label and a reset-prototype button ([dist/index.html](https://github.com/OpenCoven/open-sesame/blob/main/dist/index.html)). No document names a target user other than the owner, and the repository holds no usage data on which features the owner relies on (researchers' gap). What was built is far wider than the stated identity: roughly 25 feature areas, of which the largest by size are media and music (188 KB), live audio and voice (171 KB), Coven Familiars (137 KB), the reader (129 KB) and the computer-use agent (112 KB), measured in [dist/](https://github.com/OpenCoven/open-sesame/tree/main/dist). The project's own capability matrix says it records source contracts and not a live survey: for nearly every row only fixtures or compilation are covered, real device or provider acceptance is pending, and Windows and Linux have no qualified host ([capabilities](https://github.com/OpenCoven/open-sesame/blob/main/docs/capabilities.md)). The researchers did not run the app either, so which features work in practice is unknown.

The structure explains why that breadth is expensive. The web layer is about **1.75 MB of hand-authored, build-less source**; `index.html` loads **114 scripts and 55 stylesheets** in a fixed order, assigns 85 `window.OpenSesame*` globals and carries 848 element ids ([dist/index.html](https://github.com/OpenCoven/open-sesame/blob/main/dist/index.html)). Styling has accreted into one 174 KB base sheet followed by 54 override sheets, six of them named "polish" or "refinement", with **511 `!important` declarations** ([dist/](https://github.com/OpenCoven/open-sesame/tree/main/dist)). Three different mechanisms are all called "widgets": a visibility switch for 20 built-in features of which four start active ([widget-lifecycle.js](https://github.com/OpenCoven/open-sesame/blob/main/dist/widget-lifecycle.js)), a closed JSON format for "declarative tools" limited to five pre-approved operations ([docs/tools.md](https://github.com/OpenCoven/open-sesame/blob/main/docs/tools.md)), and page adapters that add tabs ([page-widgets.js](https://github.com/OpenCoven/open-sesame/blob/main/dist/page-widgets.js)). Installing a widget never loads code; it only reveals a surface that is already bundled, so an uninstalled widget costs the same parse time and DOM as an active one (researchers' inference from the load list).

The history shows how it got here. Everything documented happened in about nine days, almost entirely through AI coding agents on parallel `codex/*` branches, with release labels running from v0.0.1 to v0.0.19 ([work-tracking history](https://github.com/OpenCoven/open-sesame/blob/main/docs/archive/2026-11-08-work-tracking-history.md)). The recurring problems on record are global-name collisions, layout and fit regressions, PTY shutdown stalls and audio start-up repairs, and the polish plan records that rendered surfaces were never accepted on hardware because visual automation was unavailable to the agents ([polish plan](https://github.com/OpenCoven/open-sesame/blob/main/docs/desktop-polish-plan.md)). The researchers' inference is that these failures are structural to the shared-globals, ordered-cascade design of `dist/`, and that the Tauri design deletes the 428 KB Swift and Python host while keeping that 1.75 MB UI as it is.

Two ecosystem facts sharpen the question of purpose. First, OpenCoven already ships two cross-platform Tauri clients for talking to familiars: `chat` (Tauri plus React, with a noVNC viewer) and `coven-cave` (Next.js in Tauri 2, with chat, boards, GitHub triage, terminal and browser panes) ([chat](https://github.com/OpenCoven/chat), [coven-cave](https://github.com/OpenCoven/coven-cave)). The parts unique to Open Sesame are the personal-organiser layer and the summonable widget form factor (researchers' inference). Second, the approved Tauri design leaves out the notch panel and the global shortcut, which are the access mechanisms that made the app a widget, while porting agent-side features such as Familiars, the agent monitor, the GitHub monitor and Image Studio. As written, the first Tauri release would be an agent console in an ordinary window, which is the territory the sibling apps and the labs already hold.

## The labs own the command centre, wrappers keep dying, and three positions stay thin

The competitive field in November 2026 falls into six lanes. The table summarises them; the paragraphs after it draw out what matters for Open Sesame.

| Lane | Representative products | State in November 2026 | Consequence for Open Sesame |
|---|---|---|---|
| First-party command centres | Claude desktop (Code and Cowork), Codex app / ChatGPT desktop, Cursor 3, Factory | Parallel sessions, worktrees, terminals, browser panes, scheduled tasks, computer use; Claude and ChatGPT now on Linux in beta or preview | Each runs only its vendor's agent; do not compete on depth |
| Third-party CLI wrappers | Conductor, Vibe Kanban, Nimbalyst, Emdash, Superset, AgentsRoom, Claude Squad | Crowded, mostly free, Mac-first, commercially unstable | Local orchestration is expected to be free |
| Launchers | Raycast, Alfred, PowerToys Command Palette, Vicinae | Raycast on macOS, Windows and iOS with metered AI credits; no official Raycast on Linux | A palette is table stakes, not a product |
| Notch and menu-bar companions | NotchNook, Alcove, Boring Notch; agent-status apps such as Vibe Island | Busy, cheap, macOS-only | The agent-status idea is validated, but only on Mac |
| All-in-one workspaces | Notion, Obsidian, Sunsama, Akiflow | Sustained by team platforms or by a free local core with paid services | Bundles draw slowness and complexity complaints |
| Terminal-centred tools | Warp, Wave Terminal, iTerm2, cmux, Tabby | Wave is the closest structural analogue | Terminal plus AI panel already exists free on three OSes |

The labs have closed most of the feature gap. Claude's desktop app runs sessions side by side with optional worktree isolation, an integrated terminal, a browser pane, connectors and plugins, on macOS, Windows and a Linux beta ([Claude Code docs](https://code.claude.com/docs/en/desktop)). OpenAI's Codex app became the base of a planned "superapp" in April 2026 with background computer use, an in-app browser, image generation, automations and SSH ([The New Stack](https://thenewstack.io/openais-superapp-takes-shape/)), and ChatGPT desktop reached Linux in public preview in August 2026 ([OMG! Ubuntu](https://www.omgubuntu.co.uk/2026/08/chatgpt-desktop-app-linux-preview)). The researchers' inference is that cross-platform reach alone no longer separates a small product from the labs, and that the labs' feature lists now overlap most of the agent-side features Open Sesame built.

The wrapper lane is a warning. Meta acquired Conductor on 4 November 2026, eight months after a $22M Series A; sign-ups stopped that day, its cloud shuts down on 20 November, and the Mac app loses support in early 2027 ([SiliconANGLE](https://siliconangle.com/2026/11/04/meta-acquires-ai-coding-startup-conductor-whose-app-runs-several-coding-agents-at-once/)). Bloop shut Vibe Kanban's services in April 2026 because most of its daily users were on free plans and the founders found no business model they wanted ([Vibe Kanban](https://vibekanban.com/blog/shutdown)). Crystal was deprecated, Terragon is described as dead, and Opcode is no longer actively developed, according to vendor roundups ([AgentsRoom](https://agentsroom.dev/blog/best-multi-agent-coding-tools), [Nimbalyst](https://nimbalyst-website.pages.dev/blog/best-agent-management-tools-2026/)). Superset pledges that local parallel agents will never require payment ([Superset](https://github.com/superset-sh/superset)). Nothing in the sources shows willingness to pay for a local single-user orchestration or widget app beyond roughly $30 one-time or a few dollars a month (researchers' inference); the money visible in the sources sits with model subscriptions, cloud execution, mobile and team features, and daily planners at $15 to $34 a month ([Morgen](https://morgen.so/blog-posts/sunsama-vs-akiflow)).

What users say they want is attention management, not more agents. Developers on Hacker News mostly report one to three useful parallel threads and name review capacity, merge conflicts and context switching as the limits ([Hacker News](https://hn.nuxt.dev/item/47573483)). An InfoWorld piece from September 2026 lists the wanted features as shortcuts to the agent awaiting a decision, grouping by project, tasks that keep their purpose and evidence, and urgency triage ([InfoWorld](https://www.infoworld.com/article/4221481/the-best-ide-for-agentic-ai-may-not-be-an-ide-at-all.html)). The products that answer this directly are the agent-status notch apps, all five of which in one vendor comparison are native macOS apps ([Vibe Island](https://vibeisland.app/alternatives/)), and cmux, a macOS-only terminal whose panes ring when an agent is waiting ([cmux](https://github.com/manaflow-ai/cmux)).

From this the researchers identify three thinly occupied positions. The first is multi-vendor CLI sessions with a GUI on Windows and Linux, where the sources show only Emdash, Nimbalyst and AgentsRoom ([Emdash](https://github.com/generalaction/emdash)). The second is agent-status and approval surfaces on Windows and Linux, where none was found, with the caveat that the researchers did not search exhaustively. The third is personal widgets combined with agent sessions and real terminals in one local app, which no reviewed source describes; Wave Terminal is nearest on the terminal side, offering terminal, SSH, browser and file-preview blocks with bring-your-own-key AI for free on three operating systems ([Wave](https://github.com/wavetermdev/waveterm)), though a March 2026 review found running CLI agents inside it awkward ([MOLTamp review, a vendor source](https://moltamp-site.pages.dev/blog/wave-terminal-review-2026)). The same evidence sets two constraints: bundles attract performance and complexity complaints, with Notion the usual example and local-first Obsidian the counter-example ([Unstar](https://unstar.app/blog/productivity-app-reviews-what-power-users-complain-about-2026)), and no source measures demand for a combined widget-plus-agent desktop on any operating system.

## Design it for people who run CLI agents, with the owner as first user

**Judgment.** Open Sesame should be designed as a panel you summon, not a workspace you live in. Its job in one sentence: show what your agents and your day need from you, let you act on it in seconds, and get out of the way. The primary user is a developer who already runs Claude Code, Codex, OpenCode or similar tools in terminals and wants one place that works the same on macOS, Windows and Linux. The owner fits that description and is the only user today, so the test for every feature in the restart is whether the owner uses it daily.

Four strands of evidence support that position. Demand is for triage of which agent needs a decision, as the previous section showed. The surfaces that answer it exist only on macOS, while the Tauri move puts Windows and Linux within reach. The labs' apps are single-vendor, so a neutral panel that watches all of a user's CLIs does something they will not. And the personal layer (notes, tasks, focus) is the part of Open Sesame that neither sibling OpenCoven app nor any wrapper offers.

The same evidence says what the product should not be. It should not be a worktree orchestrator, because that lane is free, crowded and losing its best-known members. It should not be a second chat client for familiars, because `chat` and `coven-cave` already are. It should not be an everything app: the feature-fatigue research found people choose feature-rich products and are then less satisfied using them ([Thompson, Hamilton and Rust, abstract](https://synapsesocial.com/papers/W2105037366)), although that study concerns consumer electronics and applies here only by analogy. Raycast's users objected in September 2026 when an AI add-on began to drive the price of a launcher they valued for other reasons ([ifun.de](https://www.ifun.de/raycast-veraergert-nutzer-mit-neuem-ki-preismodell-288857/)), and Microsoft conceded that Windows 11 widgets felt distracting and turned the feed and badges off by default ([Neowin](https://www.neowin.net/news/microsoft-admits-windows-11-widgets-are-distracting-and-overwhelming-announces-fixes/)). Calm and peripheral is the safer default.

One existing piece of the code already expresses this purpose. The mobile presentation has a "Today" overlay showing the latest note, open tasks, the focus clock and the reader's saved count, but the desktop has no Today page ([mobile shell doc](https://github.com/OpenCoven/open-sesame/blob/main/docs/mobile-shell.md)). Judgment: the desktop summon view should be that Today view with one addition, the list of agents and whether each is working, waiting or finished.

The honest limit of this recommendation is that it rests on product behaviour, journalism and forum posts. No user research compares summon patterns, no source sizes the market, and the Conductor users now looking for alternatives are on macOS, where the field is most crowded.

## Five defaults, a short optional shelf, and widgets that load nothing until asked

The researchers offer a rule for what is core (their inference): a feature belongs in the default set if the first session is useful with it and without configuration, if other features depend on it, or if it carries no meaningful permission or platform risk. Everything with a heavy dependency, platform-specific behaviour or a niche audience is a widget that stays dormant until enabled. The current defaults already lean this way: the four active widgets on a fresh profile are Agenda, Local Media, Tasks and Shells, and every feature that needs an external CLI, a capture permission or a third-party account starts uninstalled ([widget-lifecycle.js](https://github.com/OpenCoven/open-sesame/blob/main/dist/widget-lifecycle.js)). The table below is this report's judgment applying that rule to the inventory.

| Tier | What goes in it | Reason |
|---|---|---|
| Core, always present | Window, tray and summon; command palette with capture, calculator and world clock; settings; Rust-owned storage; the widget switchboard; optional account | Other features depend on them; all are web-only or thin native shell |
| On by default | Today view; Projects (notes, tasks, bookmarks as one surface); Focus timer; Shells (local and SSH); Agents (who is running, who is waiting) | Useful in the first session with no setup; local machine only |
| Optional, off until enabled | Reader and RSS; GitHub monitor (needs `gh`); Coven Familiars (needs `coven`); local media; remote desktops over `wss://`; local transcription once a model path exists | External CLI, account, model download or niche audience |
| Left out of the restart | Protected Share; iMessage controllers; speaker diarization; Spotify, Apple Music and YouTube account flows and embedded players; Image Studio; Claude/Codex Live Q&A; the embedded computer-use engine; Screen notes; prototype settings sidebar, Present mode and guide dialog | macOS-only capture stacks, third-party account friction, duplication of first-party apps, or residue |

Three choices in that table go beyond the Tauri design. Notes and bookmarks move into the default set, because they are pure web features with local storage that today start uninstalled while Local Media starts active. Image Studio leaves, because it depends on a Codex CLI signed in with a ChatGPT account ([capabilities](https://github.com/OpenCoven/open-sesame/blob/main/docs/capabilities.md)) and the Codex app now generates images itself ([The New Stack](https://thenewstack.io/openais-superapp-takes-shape/)). Coven Familiars becomes optional and is ported after the core, because it is the largest single port in the plan (Task 7 translates 37 tests, 32 of them for one 39 KB Python module) and duplicates what `chat` and `coven-cave` already do; this last point is a decision for the owner, discussed in the final section.

### How the widget system should work

The model with the strongest evidence is VS Code's: extensions, including bundled ones, declare activation events and load only when one fires, and since version 1.74 contributed commands and views generate those events from the manifest ([VS Code activation events](https://code.visualstudio.com/api/references/activation-events)). Applied here (researchers' inference): treat every widget, first-party ones included, as an entry with a manifest that lists its commands, palette entries, panel and settings, so the palette can list everything without loading any widget code, and "default" means pre-enabled, not loaded at startup. Judgment: collapse the three lifecycle states into two (on and off), since consumers only test `isActive` and "inactive" and "uninstalled" behave identically at runtime (researchers' inference), and settle on the single word "widget" in place of the three vocabularies the repository map documents ([repository map](https://github.com/OpenCoven/open-sesame/blob/main/docs/repository-map.md)).

Security decides how far extensibility can go. Tauri's capability system grants permissions per window or webview, not per iframe, and on Linux Tauri cannot distinguish an iframe's IPC requests from the window's ([Tauri capabilities](https://v2.tauri.app/security/capabilities/)). The plan exposes `window.__TAURI__` globally and routes everything through one `bridge_request` command gated on the window label `main`. The researchers' inference is direct: any script that runs in the main document has the full signed-in bridge, so the label check does not isolate widgets. That is acceptable while every line of JavaScript in the window is first-party. It stops being acceptable the moment third-party code is loaded as a script.

The surveyed products suggest a tiering (researchers' inference). First-party widgets ship in the bundle and load lazily. Declarative widgets are JSON interpreted by first-party renderer code, which is the cheapest safe tier and already exists. Third-party interactive widgets, if they ever arrive, run in a sandboxed iframe with no Tauri API inside and talk to the host through a narrow postMessage protocol with declared permissions; the MCP Apps extension standardises exactly that shape, with mandatory iframe sandboxing and predeclared templates ([SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)) and a network policy that denies everything a widget has not declared ([MCP Apps draft specification](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx)). Full-trust plugins are the Obsidian model, where the vendor says it cannot reliably restrict plugins and ships with third-party code disabled by default ([Obsidian](https://obsidian.md/help/plugin-security)). Judgment, in keeping with the request not to over-complicate: build only the first two tiers now, write the manifest format, and defer the iframe tier until someone other than the owner wants to write a widget. When that day comes, authorisation must be enforced in Rust per request by widget identity and declared capability, never by origin or label alone. Whether a sandboxed iframe in a Tauri window can still reach the parent's IPC on each platform was not tested by the researchers.

## One pre-warmed window everywhere, with platform upgrades layered on top

The convention among AI and launcher-style desktop apps in 2026 is a global hotkey that opens a small floating input over the current app, backed by a tray icon and a full window: Google's and OpenAI's apps use Option+Space or Alt+Space, and Claude uses a double-tap of Option on Mac or Ctrl+Alt+Space on Windows ([Fast Company](https://fastcompany.com/91602750/why-ai-wants-to-take-over-your-desktop)). Users react when that path changes: after a macOS update routed Option+Space to Codex, people on OpenAI's forum asked for the quick companion window back because it gave them side answers without interrupting their main session ([OpenAI community](https://community.openai.com/t/companion-window-should-stay-available-for-chatgpt-not-only-codex/1386295)). What makes a summon feel instant is keeping the webview alive: one Tauri author measured about one second from process start to painted window on macOS, against a near-instant call to show a window that was hidden instead of destroyed ([tinyforge](https://dev.to/tinyforge/tauri-cold-launch-was-1s-heres-how-i-got-it-to-feel-instant-32lh)).

Only two summon paths are dependable on all three systems from one Tauri codebase: a tray icon with a context menu, and an ordinary window that can be raised by launching the app again or by a deep link (researchers' inference). The reliability of everything else varies by platform, as the researchers' matrix shows.

| Pattern | macOS | Windows | Linux X11 | Linux Wayland |
|---|---|---|---|---|
| Tray icon with menu | Yes | Yes | Yes, menu only (GNOME may need an extension, unverified) | Same as X11 |
| Left-click popover anchored to tray icon | Yes | Yes | No | No |
| Global hotkey through the Tauri plugin | Yes | Yes | Yes | No |
| Floating always-on-top panel | Yes, with `tauri-nspanel` | Yes | Mostly | No guarantee |
| Notch overlay | Yes, custom | Not applicable | Not applicable | Not applicable |
| Normal window raised by second launch or deep link | Yes | Yes | Yes | Yes |

The Linux rows rest on documented limits. Tauri's tray emits no click events on Linux, so only the right-click menu works ([Tauri system tray](https://v2.tauri.app/learn/system-tray/)). A Tauri maintainer confirmed in September 2025 that global shortcuts were still unsupported on Wayland ([Tauri discussion](https://github.com/tauri-apps/tauri/discussions/10017)), and on GNOME under Wayland window positioning, always-on-top and skip-taskbar silently do nothing ([Tauri issue 14913](https://github.com/tauri-apps/tauri/issues/14913)). The XDG GlobalShortcuts portal lets an app request a shortcut that the user approves, but the trigger is a preference and not a guarantee ([XDG portal docs](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html)). 1Password, which faces the same wall, documents a tray-menu entry as the alternative to its Linux shortcut ([1Password](https://support.1password.com/quick-access/)).

The recommended design follows from that (researchers' inference, which this report adopts). The baseline on every system is a normal, centred, pre-warmed window that is shown by the tray menu, by launching the app again through the single-instance plugin, by an `opensesame://` deep link, or by a command-line toggle such as `open-sesame --toggle`. On macOS, add a global hotkey and convert the window to an `NSPanel` with `tauri-nspanel`, which is what lets a panel appear over full-screen apps and other Spaces ([tauri-nspanel](https://www.github.com/ahkohd/tauri-nspanel)). On Windows, add the hotkey and a tray-anchored popover; focus works because the hotkey gives the process the last input event, which is the condition Windows sets for taking the foreground ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)). On X11, add the hotkey. On Wayland, try the portal and otherwise tell the user to bind a desktop shortcut to the toggle command, and do not attempt to position the window. The Windows Widgets Board is poor value: it requires a packaged app identity that Tauri's EXE and MSI installers do not provide, and HTML widgets are limited to the European Economic Area ([Microsoft Learn](https://learn.microsoft.com/windows/apps/design/widgets), [Tauri Microsoft Store guide](https://v2.tauri.app/distribute/microsoft-store/)).

Three details matter in practice. The default shortcut must be configurable and must detect registration failure, because Option or Alt plus Space is already claimed by ChatGPT, Gemini and Raycast-style launchers (researchers' inference). Hide-on-blur must be suspended while a native dialog, a browser sign-in or a drag is in flight, a gotcha one Tauri menubar author reports ([DEV write-up](https://dev.to/hiyoyok/building-a-menubar-app-with-tauri-v2-what-nobody-tells-you-2nae)). And the summon view should be tuned for capture, search and glanceable status, with terminals and long agent sessions in the full window. Judgment: the notch can wait. It is macOS-only, the agent-status notch niche already has five entrants there, and the hotkey panel is its cross-platform equivalent.

**Conflict with the plan.** Task 3 of the plan makes closing the window quit the app, and the design lists the global shortcut as not ported. That removes both the instant re-summon and the convention users expect. The trade-off is real: a process that stays alive in the tray holds memory and needs an explicit Quit, and the plan's simpler lifecycle makes the no-leftover-processes guarantee easier to test. The research favours hide-to-tray plus a hotkey, because without them the app is no longer a companion. The plan's `window.keepOpen` method (always-on-top) will also silently fail on GNOME under Wayland and should return the design's existing not-available-on-this-OS error there.

### Sign-in is part of access, and making it mandatory conflicts with the evidence

**Conflict with the plan.** The design's request gate requires a signed-in, unexpired session for every method except the auth calls, limited system info and window focus. The mechanics are sound: system browser, PKCE, exact callback validation and a refresh token in the OS credential store match RFC 8252 ([RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252)) and WorkOS's own desktop example ([WorkOS example](https://github.com/workos/electron-authkit-example)). The conflict is with making it mandatory for local features. Warp required login, heard from hundreds of developers that the requirement stopped them using or recommending the product, and in November 2024 made core features usable without an account while keeping AI and team features behind sign-in ([Warp](https://www.warp.dev/blog/lifting-login-requirement)). That is one company's experience, and no survey data was found, but its audience is the same one Open Sesame would address. Today nothing in Open Sesame is cloud-backed: the capability matrix says items and settings are local and account sync is not a qualified feature ([capabilities](https://github.com/OpenCoven/open-sesame/blob/main/docs/capabilities.md)). The researchers also infer that, as designed, the app locks the user out of local terminals and notes when offline at token expiry.

The trade-off, stated plainly: mandatory sign-in gives the owner a known user list and a single control point at the moment of public distribution, and a one-rule gate is simpler to test. Optional sign-in costs a second class of methods in the gate and gives up that control, in exchange for lower adoption friction and no offline lockout. This report's judgment is to keep WorkOS exactly as built and require it only for features that have an account-backed reason to exist, which today is none and later would be sync or mobile, the same services the market evidence says people pay for. If the owner keeps it mandatory, two mitigations still apply: an offline grace period for local features, and a loopback redirect as a fallback on Windows and Linux, because custom-scheme callbacks arrive there as a command-line argument any local process can spoof and AppImages lose scheme registration when moved ([Tauri deep linking](https://v2.tauri.app/plugin/deep-linking/)). Whether WorkOS AuthKit accepts loopback redirects with a dynamic port was not confirmed. The scheme `opensesame` is also not reverse-domain, which RFC 8252 says servers should reject, although WorkOS evidently accepts plain schemes (researchers' inference). On Linux the Secret Service may be absent, so the credential store needs an explicit fallback message.

## Stop loading 114 scripts, stream terminals over channels, and move data into Rust

### Startup and memory

The measured case for Tauri is real but thin. A single-run macOS benchmark of scaffold apps from July 2025 found a Tauri bundle of 8.6 MiB against 244 MiB for Electron and about 172 MB of memory against about 409 MB, with startup differences negligible ([Hopp](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4)); a census of 10,778 Mac apps put the median Tauri app at 26.2 MB and the median Electron app at 406.9 MB ([Desktop Insights](https://desktopinsights.com/blog/state-of-desktop-app-runtimes-2026)). No independent 2026 benchmark covers all three operating systems, and no measured cold-start figures for WebView2 or WebKitGTK under Tauri were found. The practical levers are therefore the ones the app controls: keep the webview alive and hidden, and load less. The researchers' budget is that nothing but the shell, auth state, palette index and last-used view loads before first paint, verified with a startup trace on each OS. On Windows, Microsoft's guidance is to keep the WebView2 user-data folder on a fast local disk, prefer the Evergreen runtime and suspend inactive views ([Microsoft Learn](https://learn.microsoft.com/microsoft-edge/webview2/concepts/performance)).

Target Tauri 2.12.x, the current stable line, which raised the minimum Rust version to 1.90 ([Tauri 2.12](https://v2.tauri.app/blog/tauri-2.12/)). Tauri 3 exists only as an alpha whose selectable Chromium runtime adds hundreds of megabytes and currently runs unsandboxed on Windows ([Tauri v3 CEF docs](https://v3.tauri.app/develop/cef/)); keeping host code free of direct `tauri::wry` use preserves that escape hatch (researchers' inference). The researchers note one conflict: GitHub's releases page flagged 2.11.5 as latest while the official release index shows 2.12.3, and they treat the index as authoritative ([Tauri release index](https://v2.tauri.app/release/)).

### Front-end structure

The decision to stay framework-free and build-less is compatible with a much better structure. Served from the local `tauri://` protocol, unbundled modules avoid most of the network cost that makes them slow on the web, so native ES modules with a dynamic `import()` per widget give real lazy loading and scoping with no build step (researchers' inference); the bundler vendors' own case against unbundled modules is about network round trips ([Rolldown](https://rolldown.rs/in-depth/why-bundlers)). The highest-leverage change is not bundling but not loading every file at startup. Two cautions apply: import maps and newer CSS features such as cascade layers were not verified against the oldest WebKitGTK in the support matrix, so use relative specifiers and treat those CSS features as progressive enhancement; and Tauri's isolation application cannot use ES modules ([Tauri isolation pattern](https://v2.tauri.app/concept/inter-process-communication/isolation/)).

**Conflict with the plan.** The design keeps `dist/` unchanged apart from the transport branch in `bridge.js`. That is the fastest cutover and keeps the existing checks passing. It also carries forward every script, every global and every override sheet, including the code for all the features the gate will refuse, and with them the load-order fragility behind the recorded regressions. Judgment: since the owner is willing to start from scratch and no data is migrated, write a new small shell (still framework-free, still no build) as ES modules, and move widgets into it one at a time, leaving the rest in Git history. This respects the decision about the kind of UI while changing the decision that it stays untouched. The cost is a slower first cutover and rewritten checks for whatever moves; the saving is that checks and CSS for features that do not move simply disappear.

### Terminal streaming

**Conflict with the plan.** Task 5 sends PTY output as base64 inside `terminal.data` events emitted to the main window. Tauri's documentation says its event system is not designed for low latency or high throughput, that event payloads are always JSON strings delivered by evaluating JavaScript, and that rapid events can be handled out of order by async listeners; it describes channels as the fast, ordered mechanism Tauri itself uses for child-process output ([Tauri docs](https://v2.tauri.app/develop/calling-frontend/)). The xterm.js flow-control guide adds that the emulator ingests roughly 5 to 35 MB/s while producers can emit far more, that data beyond a write buffer of about 50 MB is discarded, and that the remedy is high and low watermarks with write callbacks used as acknowledgements ([xterm.js](https://xtermjs.org/docs/guides/flowcontrol/)). The documented-safe shape (researchers' inference) is one channel per pane, batching in Rust by time and size, and an acknowledgement watermark that pauses the PTY reader. The trade-off is that this breaks the plan's rule that event names and the envelope stay unchanged, and it means editing `terminal.js` as well as `bridge.js`. Agent CLIs produce exactly the bursty, high-volume output where the difference shows, so the change is worth making before the terminal port, not after. No primary benchmark of channels against events was retrieved. On Linux, WebGL under WebKitGTK can silently fall back to software rendering with high input latency, so xterm's WebGL renderer needs a non-WebGL fallback and a user toggle ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)).

### Storage

Today the app persists state in 37 distinct localStorage keys ([dist/](https://github.com/OpenCoven/open-sesame/tree/main/dist)). Webview storage is keyed to an origin that differs by platform (`tauri://localhost` on some, `http://tauri.localhost` on Windows) and becomes runtime-defined in the Tauri 3 alpha ([Tauri v3 alpha notes](https://newreleases.io/project/github/tauri-apps/tauri/release/tauri-v3.0.0-alpha.0)); it is also invisible to Rust, which rules out backup, export, sync and, importantly, serving the data to agents (researchers' inference). The recommended split is settings and widget enablement in Tauri's store plugin, notes, tasks, bookmarks and feeds in SQLite owned by Rust behind typed commands, tokens only in the OS credential store, and localStorage for disposable UI state alone. Typed commands matter because Tauri's SQL plugin sends raw SQL strings from the frontend and requires write permission to be granted explicitly ([Tauri SQL plugin](https://v2.tauri.app/plugin/sql/)). Because the restart carries no legacy data, this is the cheapest moment to do it. Defer sync and CRDTs; give rows stable ids and modified timestamps so either can be added later. The plan has no storage task, so this is an addition.

### Processes, environment and Linux rendering

Three smaller items protect the plan's own review goals. For subprocesses the plan's Task 6 uses a job object on Windows, but its Task 5 kills terminal sessions on Windows by dropping the ConPTY and terminating the child. A user report from October 2026 describes a runtime that killed only the top-level shell on Windows and left `node.exe` grandchildren running, with a kill-on-close job object as the suggested remedy ([Cursor forum](https://forum.cursor.com/t/cursor-sdk-local-runtime-on-windows-background-shells-are-only-partially-killed-at-the-end-of-a-run-so-grandchild-processes-are-orphaned-and-keep-running/176867)); PTY sessions should get the same job-object treatment. Second, the plan resolves CLIs from `PATH`, but packaged GUI apps on macOS and Linux do not inherit the login shell's environment; T3 Code's packaged app corrupted its `PATH` under the fish shell and could not spawn `codex` or `git` until it printed the variable in a shell-agnostic way and added fallbacks ([t3code issue](https://gh.hhj520.top/pingdotgg/t3code/issues/218)). Resolve the user's environment once at startup, probe known install locations, and offer an override in settings. Third, the design says browser fallbacks such as browser speech recognition keep working where the webview supports them; default WebKitGTK builds lack WebRTC ([Tauri discussion](https://github.com/tauri-apps/tauri/discussions/8426)), so on Linux those features should be reported as unavailable. Linux also needs a compatibility-mode setting, because Tauri documents blank windows and crashes on NVIDIA with Wayland and environment-variable workarounds that slow everyone if applied unconditionally ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)).

### Distribution has three long-lead items

The plan puts installers, signing and auto-update out of scope, which is reasonable for a first build but not for a public release planned soon, because three items have lead times. Apple requires a paid developer account at 99 USD a year, a Developer ID certificate and notarization ([Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/)). On Windows, Azure Artifact Signing costs about 9.99 USD a month, is available to organisations in the USA, Canada, EU and UK but to individuals only in the USA and Canada, and takes a few business days of identity validation; even signed, new files can show SmartScreen warnings until reputation builds ([Microsoft Learn](https://learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options)). The Tauri updater needs its own signing key, and if that key is lost existing installs can never be updated; its Linux update artefact is AppImage, and deb, rpm and Flatpak are not covered ([Tauri updater](https://v2.tauri.app/plugin/updater/)). The Mac App Store is a poor fit because its sandbox conflicts with spawning shells and driving installed CLIs (researchers' inference). Judgment: the plan also keeps the bundle identifier `com.perch.widgetstudio`, a leftover from an earlier product name. Change it before the first public build: the identifier is what the operating system and Tauri key the app's identity on, renaming it later means a migration, and today there is nothing to migrate.

## Local models: an endpoint setting first, transcription second, never the agent's brain

The integration surface has converged. By late 2026 llama.cpp's server, Ollama and LM Studio all expose OpenAI-compatible and Anthropic-compatible endpoints with tool calling, so one HTTP client can target any of them; llama.cpp and Ollama are MIT-licensed and redistributable, while LM Studio's terms forbid redistribution or embedding without an enterprise agreement ([runtime comparison](https://www.developersdigest.tech/local-models/runtimes/compare/mlx-lm-vs-llama-cpp), [Ollama](https://github.com/ollama/ollama), [LM Studio guide](https://codersera.com/blog/lm-studio-complete-guide-2026/)). The established pattern for large chat models is to connect to a server the user already runs: Zed does this ([Zed](https://zed.dev/blog/local-ai-in-zed)) and Raycast routes local models through Ollama ([Raycast manual](https://manual.raycast.com/ai/local-models)). Operating-system models from Apple, Microsoft and Chrome are free and need no download but are single-platform, small-context and not documented as reachable from a Tauri webview (researchers' inference).

What local models are good for is narrow, repeated, low-stakes work. A practitioner roundup from October 2026 finds small models succeed at classification, extraction, routing and short grounded answers and recommends testing a 4B and a 9B model on one's own tasks and escalating only failures ([vdf.ai](https://vdf.ai/blog/best-small-language-models/)). An academic evaluation found that naively swapping a frontier model for a 9B local one cut agent accuracy by 25 to 39 points, and that the gap closed to about 3 points only after jointly tuning prompts, tools, runtime and weights ([OpenJarvis, arXiv](https://arxiv.org/pdf/2605.17172)). For coding agents the verdict from people who ran them is consistent: one author's November 2026 tests found a 16 GB Mac unworkable and local Codex sessions suitable for a single function or script, not multi-file changes ([michaelwolfinger.com](https://michaelwolfinger.com/blog/2026/codex-cli-local-model-lm-studio-ollama/)), and another does not recommend local agentic coding at all after an offline trial ([williamangel.net](https://www.williamangel.net/blog/2026/04/27/offline-agentic-coding.html)). The researchers put the practical hardware floor for a local coding agent at a 24 GB NVIDIA GPU or a 48 to 64 GB Apple M-series machine.

Speech is the exception where local is simply good. NVIDIA's Parakeet TDT 0.6B v3 and several other open models beat Whisper large-v3 on the English Open ASR average ([speechtotext.dev](https://speechtotext.dev/leaderboard/)), Moonshine v2 reports sub-300 ms English streaming latency on an Apple M3 ([arXiv](https://arxiv.org/html/2602.12241)), and Rust paths exist: `transcribe-rs` runs Parakeet, Moonshine and Whisper through ONNX Runtime and whisper.cpp ([transcribe-rs](https://docs.rs/crate/transcribe-rs)), and Handy is a shipping MIT-licensed Tauri 2 dictation app with an in-process Rust speech stack ([Handy](https://github.com/cjpais/Handy)). That makes local transcription the natural cross-platform replacement for the Apple speech stack the Tauri design drops. Rust-native diarization exists but is young and needs in-house validation (researchers' inference).

**Judgment on the role local models should play**, in order of adoption. In the first release, nothing in the app requires a model, and there is no bundled runtime; settings carry one field for an OpenAI-compatible endpoint. The first local feature to add afterwards is transcription as an optional widget, with the model downloaded on first use into the user data directory with progress and size verification, which is the pattern Liquid AI's desktop guidance recommends for model files generally ([Liquid AI](https://docs.liquid.ai/deployment/on-device/llama-cpp/desktop)). After that, small utility tasks (titling, tagging, short summaries, dictation clean-up) through the endpoint with schema-constrained output and validate-and-retry, which the researchers identify as what makes small models dependable. Semantic search over notes with a sub-1 GB embedding model and `sqlite-vec` fits the SQLite design, though `sqlite-vec` is still a pre-1.0 alpha ([sqlite-vec listing](https://openapps.pro/packages/sqlite-vec)). Local coding agents stay an opt-in endpoint the user points their CLI at. Local image generation stays out: the permissively licensed models need 12 to 16 GB downloads and run for tens of seconds to minutes on typical Macs ([modelfit.io](https://modelfit.io/guides/local-image-generation-mac/)).

Two housekeeping rules follow from the licensing research. Keep any in-app catalogue to Apache-2.0 and MIT weights plus CC-BY-4.0 speech models with visible attribution, because a growing set of 2026 releases carry revenue caps, non-commercial terms or geographic exclusions ([code4u.app](https://www.code4u.app/blog/open-weight-ai-model-licenses-commercial-use)). And do not promise "local" without checking: Ollama now includes cloud routing that must be disabled with an environment variable ([insiderllm.com](https://insiderllm.com/guides/ollama-0-17-new-features/)). Many of the 2026 model names and benchmark figures in the research came from aggregators or vendors and were not independently verified; none of the recommendations above depends on a specific model.

## Harnesses: terminals first, an MCP server second, ACP third, and never touch a credential

Today Open Sesame reaches agents three ways: real PTY panes, a Familiars chat that shells out to `coven run` with a harness drawn from `coven-code`, `codex` or `claude` ([coven_runtime.py](https://github.com/OpenCoven/open-sesame/blob/main/desktop/coven_runtime.py)), and a process monitor that recognises Codex, Claude Code, Coven, Gemini CLI, Aider and OpenCode ([agent-monitor.js](https://github.com/OpenCoven/open-sesame/blob/main/dist/agent-monitor.js)). OpenCode and Gemini are detected but are not selectable harnesses anywhere in the code (researchers' inference). The table sets out what each target offers a Rust host and what its vendor permits.

| Target | Machine interface for a Rust host | Position on consumer subscriptions in third-party apps | Recommended use |
|---|---|---|---|
| Claude Code | `claude -p` with stream-JSON in both directions; 33 hook events including an HTTP hook type; no Rust SDK; ACP only through a Node adapter built on the Agent SDK | Third-party products may not offer Claude.ai login or route requests through Free, Pro or Max credentials, the Agent SDK included, unless approved; an end user signing in to the unmodified binary is carved out | PTY pane now; later `-p` against the user's installed binary; hooks for status; do not bundle the SDK or adapter |
| Codex | `codex app-server`: JSON-RPC over stdio from a native binary, with a schema generator, approval requests and rate-limit buckets | A published plan-usage flow exists for open-source, locally hosted apps; app-server authentication is stated as never permitted for commercial or hosted services | PTY pane now; app-server as the first structured integration; Codex runs its own login |
| OpenCode | Local HTTP service with OpenAPI and SSE; 2.0 runs as a background service; speaks ACP | Removed Claude Pro/Max support in February 2026 citing Anthropic legal requests | PTY pane now; SSE events for status; ACP later |
| Gemini CLI / Antigravity | Gemini CLI has headless JSONL and ACP, but was replaced for consumer accounts by the closed-source Antigravity CLI on 18 June 2026 | Terms forbid third-party software from accessing the service; users report suspensions | User-started PTY only; API key for anything structured |
| ACP | Rust crate `agent-client-protocol` 5.2.0; about 50 agents listed | A protocol; each agent's own terms apply | Third step, pinned and behind the app's own trait |
| MCP | Rust SDK `rmcp` 3.9.0 targeting the stateless 2026-07-28 specification | Not applicable | Second step: the app's own server |

The policy rows are the constraint that shapes everything else, and the researchers offer no legal conclusion. Anthropic's legal page says third-party developers may not offer Claude.ai login in their applications, route requests through consumer-plan credentials or handle those credentials, and then states that this does not prevent an end user from signing in to the unmodified Claude Code binary with their own subscription ([Claude Code legal](https://code.claude.com/docs/en/legal-and-compliance)); the Agent SDK overview repeats that offering claude.ai login requires prior approval ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). Enforcement in 2026 was active: in February the page was tightened and OpenCode dropped subscription support ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access)). OpenAI publishes a plan-usage flow for open-source, locally hosted apps, which the researchers read as the only officially documented route for a third-party app to draw on a consumer plan, and it directs paid or remotely hosted apps to an interest form ([OpenAI](https://developers.openai.com/siwc/token-sharing-open-source)), while its app-server documentation says app-server authentication was never permitted for commercial or hosted services ([Codex app-server docs](https://learn.chatgpt.com/docs/app-server)). Google's terms page says accessing the services behind Gemini CLI through third-party software violates its terms ([Gemini CLI terms](https://geminicli.com/docs/resources/tos-privacy/)), and a forum question asking whether merely running the official `agy --print` as a child process is acceptable had no staff answer as of mid-October ([Google AI forum](https://discuss.ai.google.dev/t/is-invoking-the-official-antigravity-cli-agy-print-from-a-third-party-developer-tool-an-acceptable-use/175462)).

From the wording, the pattern that most closely matches Anthropic's carve-out is launching the user's own installed, unmodified `claude` binary, with login completed in Anthropic's flow and no credential handling by the app (researchers' inference, not a legal conclusion). Three ambiguities remain open. Zed and Conductor document subscription login through adapters or a bundled Claude Code while the SDK overview requires approval, and which apps hold approval is not public ([Zed external agents](https://zed.dev/docs/ai/external-agents), [Conductor FAQ](https://www.conductor.build/docs/faq)). Whether an app that only locates and launches an existing install counts as offering Claude Code inside a product is not addressed. And `--bare` mode, which never reads OAuth credentials, is documented as the future default for `-p` ([Claude Code headless docs](https://code.claude.com/docs/en/headless)), which could change how headless subscription use works. The researchers did not fetch the Consumer or Commercial Terms themselves and found no approval programme a small app could apply to.

**Judgment: integrate in three steps, each useful alone.**

Step one is the terminal. A PTY pane running the vendor's own CLI is what every terminal does, works for every harness including ones that do not exist yet, and puts no credentials or protocol versions in the app's hands. The differentiating work in this step is the attention surface, which can be built from passive signals: the existing process scan; the state of panes the app itself owns; and, with the user's consent, Claude Code's HTTP hooks pointed at a loopback listener in the Rust core, which deliver events such as permission requests, notifications and stops with the session id and working directory ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). Consent is needed because this edits the user's Claude Code settings (researchers' inference). Transcript files should not be parsed, since Anthropic's docs warn the format is internal and can change in any release ([Claude Code sessions](https://code.claude.com/docs/en/sessions)).

Step two is the app's own MCP server. `rmcp` can embed a server in an app over stdio or Streamable HTTP ([MCP Rust SDK](https://github.com/modelcontextprotocol/rust-sdk)), and every surveyed harness accepts host-supplied MCP servers, for example through Claude Code's `--mcp-config` flag ([Claude Code headless docs](https://code.claude.com/docs/en/headless)). One implementation would then let any agent read and write the user's notes, tasks, bookmarks and feeds, independent of how the agent is driven (researchers' inference). This is the feature that joins the personal layer to the agent layer. It depends on the storage move to Rust described earlier. How each harness authenticates to a loopback HTTP server was not verified, and judgment says to prefer a small stdio shim or a per-install token over an open local port.

Step three, only if the owner wants structured chat rather than terminals, is an ACP client. ACP gives one Rust client that reaches dozens of agents with a uniform permission, diff and usage model, and it gained a registry, 1.0 SDKs and a lead maintainer from JetBrains during 2026 ([ACP updates](https://agentclientprotocol.com/updates.md)). The cautions are that the Rust crate went from 1.0.0 to 5.2.0 in under five months ([crates.io](https://crates.io/api/v1/crates/agent-client-protocol)), that Claude Code and Codex take part only through adapters ([ACP agents list](https://agentclientprotocol.com/get-started/agents.md)), and that the Claude adapter is built on the Agent SDK ([npm](https://registry.npmjs.org/@zed-industries/claude-agent-acp/latest)) and so falls under the approval note above. Pin the crate behind the app's own trait. For depth on one vendor, Codex's app-server is the easiest target for a Rust host: a native binary, documented stdio JSON-RPC and a schema generator, with no Node runtime ([Codex app-server docs](https://learn.chatgpt.com/docs/app-server)). A2A addresses coordination between remote autonomous agents and is out of scope for a single-user desktop that launches local ones (researchers' inference).

Four design rules hold across all three steps. One approval component can serve every protocol if it normalises to allow once, allow for the session, reject and cancel (researchers' inference from the three vocabularies). Approval prompts should be rendered by the native host and bound to the exact action, because approval dialogs themselves were bypassed in six AI coding assistants in 2026 according to a secondary summary of Wiz's research ([Frenchy Digital](https://frenchydigital.com/blog/computer-use-agents-browser-automation-2026)). Cost displays cannot be uniform: Claude reports dollar estimates, Codex reports percentages of plan limits, most others report tokens. And feature-detect instead of assuming versions, since Claude Code and Codex ship several releases a week. A smaller point worth checking: Anthropic allows plain statements that a product runs Claude Code but not the use of the name in a product or feature name ([Claude Code legal](https://code.claude.com/docs/en/legal-and-compliance)), and the current widget catalogue has entries titled "Claude Code" and "Codex" ([plugins-model.js](https://github.com/OpenCoven/open-sesame/blob/main/dist/plugins-model.js)); whether those entries fall under the rule is this report's question, not a finding.

## Computer use stays out of the restart, and returns only through MCP or a remote screen

The old Coven Computer feature was a macOS 14+ surface with a bundled Rust action engine pinned to a GPL-3.0 commit of `coven-code`, planning through the user's Codex or Claude CLI subscription ([engine source](https://github.com/OpenCoven/open-sesame/blob/main/desktop/engine/source.json)). The Tauri design removes it, which also removes the only GPL component from the app (researchers' inference). The research gives four reasons not to rebuild it now.

First, the labs ship it themselves. Claude's desktop app offers computer use on macOS and Windows for consumer paid plans with per-application approval and default-blocked categories ([Claude Help Center](https://support.claude.com/en/articles/14128542)), and Codex gained it on macOS in April 2026 ([OpenAI](https://openai.com/blog/codex-for-almost-everything)) and on Windows in May according to a third-party report ([Noqta](https://noqta.tn/en/news/openai-codex-computer-use-windows-2026)). The differentiating surface for a third party is narrower than in 2025 (researchers' inference). Second, the vendors themselves rank it last: Anthropic's help page orders the paths as connectors first, browser second and screen interaction as the slowest, with retries likely ([Claude Help Center](https://support.claude.com/en/articles/14128542)). Third, reliability on long tasks is still poor. Headline OSWorld-Verified scores of 83 to 86% exceed the 72.36% human baseline, but most are self-reported on differing harnesses ([Steel.dev](https://leaderboard.steel.dev/leaderboards/osworld.md)), Berkeley researchers scored 73% on OSWorld with exploits that solved nothing ([Berkeley RDI](https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/)), and on the hour-scale OSWorld 2.0 the best tracked full-completion rate is 32.0% ([Steel.dev OSWorld 2.0](https://leaderboard.steel.dev/leaderboards/osworld-2.md)). Fourth, safety is unsolved by the vendors' own account: OpenAI says prompt injection remains an open challenge it expects to work on for years ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection)), and Anthropic's docs say the model may follow instructions found in web pages or images even when they conflict with the user's ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)). Anthropic reports near-zero injection success for Claude in Chrome with its classifiers enabled ([Anthropic](https://claude.com/blog/claude-in-chrome-generally-available)), while independent adaptive-attack work, as summarised by a secondary source, defeats most published defences ([Frenchy Digital](https://frenchydigital.com/blog/computer-use-agents-browser-automation-2026)); the two should be read side by side.

The engineering cost compounds this. No single mature Rust crate covers capture, input and accessibility on all targets; working projects assemble per-platform pieces, and the public examples are small and young ([lindoelio/computer-use](https://github.com/lindoelio/computer-use)). Linux under Wayland is the weak platform: capture and input must go through portals, consent prompts recur, and one 2026 implementer hit compositor-specific failures on GNOME ([CoderLegion](https://coderlegion.com/14454/i-built-a-wayland-native-ai-computer-use-server-because-nobody-else-did)). Linux is also the one place first-party coverage is absent, so the gap is real and the cost of filling it is highest exactly there.

**Judgment: no computer use in the restart.** If it returns, the research supports two shapes that avoid building a native engine. One is to let the user's own agent drive an existing operation layer over MCP, with Open Sesame supplying the approval, stop and audit surface; Cua Driver operates native apps on all three systems and exposes an MCP interface, and the Cua project is MIT by default with some components under other licences ([Cua](https://github.com/trycua/cua)). The other is to use a remote or virtual machine as the execution surface through the app's existing VNC panes: the vendor tools exchange only screenshots and pointer or key actions, so any channel that returns a frame and accepts input satisfies the contract, and it sidesteps the Wayland input problem on the host (researchers' inference; no source measured speed or fidelity for VNC-driven agents). Either way, 2026 practice sets the minimum controls: foreground-only operation with a visible stop, per-application approval with default-deny categories such as trading, terminals and administrator prompts blocked by default, native-rendered approvals, an audit log, and explicit user consent, which Anthropic's docs require of integrators ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)). Two questions were left unresearched and matter before any return: whether running computer use through a consumer Claude Code or Codex subscription from a third-party app is permitted, and whether the vendors' screenshot classifiers still apply when screenshots reach the model through those CLIs.

## What the owner can do with this: amend the plan, cut the long tail, decide six things

### Changes to the written plan

Everything in the plan's Tasks 1 to 6 that concerns the Rust core's shape (a Tauri-free core crate, the bounded subprocess runner, callback validation, headless tests on three operating systems) is consistent with the research and should stay. The table lists what should change, in rough order of importance. Each row is this report's judgment grounded in the evidence cited in the sections above.

| # | In the design or plan today | Recommended change | What it costs |
|---|---|---|---|
| 1 | Gate step 4: every method except auth, limited system info and window focus needs a session | Keep WorkOS; require a session only for account-backed features; local features run signed out; add offline grace and a loopback redirect fallback | Two classes of methods in the gate; no guaranteed user list |
| 2 | Task 5: PTY output as base64 in `terminal.data` events | One Tauri channel per pane, batching in Rust, acknowledgement watermarks that pause the reader; non-WebGL fallback on Linux | Breaks the plan's rule that events stay unchanged; edits `terminal.js` |
| 3 | Task 3: closing the window quits; global shortcut not ported | Close hides to tray with the webview kept warm; add the global-shortcut plugin, a `--toggle` argument through single-instance, and a configurable hotkey with failure detection | A resident process; explicit Quit path to test |
| 4 | `dist/` unchanged; all 114 scripts load | New framework-free shell as ES modules; widgets imported on activation; move in only the default set first | Slower cutover; checks rewritten for what moves |
| 5 | No storage task; items stay in 37 localStorage keys | Add a task: SQLite owned by the core for notes, tasks, bookmarks and feeds; store plugin for settings | UI item code calls the bridge |
| 6 | Tasks 7 to 10 port Familiars, GitHub, reader and Image Studio before the Task 12 smoke pass | Run the three-OS smoke pass right after shell, sign-in, terminal and storage; then admit optional widgets one at a time; drop Image Studio | A first release with fewer features |
| 7 | Task 5: Windows sessions killed by dropping the ConPTY | Put every PTY child in a kill-on-close job object, as Task 6 already does for subprocesses | Small |
| 8 | CLIs resolved from inherited `PATH` | Resolve the login-shell environment once, probe known install paths, offer a settings override | Small |
| 9 | Window label `main` treated as the trust boundary, with `window.__TAURI__` global | Keep for first-party code; record a rule that no third-party script ever runs in the main document; authorise per widget in Rust when third parties arrive | Nothing now |

Row 6 deserves a sentence of defence because it reorders the plan more than it changes it. The project's own record is of features that compiled and passed synthetic checks without ever being accepted on a device, and the plan states it was written without compiling anything. Getting a thin vertical slice (window, tray, hotkey, one terminal, notes and tasks in SQLite) running and observed on macOS, Windows and Linux before porting anything else is the direct remedy.

### What to cut

Beyond the features the Tauri design already drops, judgment says to leave these behind for good unless the owner's daily use says otherwise: Protected Share, the iMessage controllers, speaker diarization with its 471 MB checkpoint, the Spotify, Apple Music and YouTube account flows, Image Studio, the Claude and Codex Live Q&A, and the embedded computer-use engine. From the code that remains, cut the prototype residue (the studio settings sidebar, Present mode, the guide dialog, the demo transcript timers), the third lifecycle state, the legacy storage keys and aliases kept for compatibility with data nobody has, and the six polish stylesheets, which a new shell would never load. On the tooling side, the 74 `check-*.mjs` scripts total 357 KB and many assert against source text or a simulated DOM (researchers' inference); when a feature does not move into the new shell, delete its checks instead of retargeting them as Task 11 proposes, and let the three-OS smoke pass carry the weight the checks could not. Finally, with one user and one branch, the task-claim and evidence protocol built for parallel agents is overhead that, by the project's own matrix, did not produce device acceptance; keep the bounded verifier and drop the rest.

### Order of work

The sequence that follows from all of this, as judgment: first, make the decisions listed below and amend the plan, and start the signing enrolments because they take calendar time. Second, build the walking skeleton and observe it on three operating systems: Tauri shell, optional sign-in, hide and show with tray and hotkey, one terminal pane streaming over a channel, SQLite, and the Today, Projects and Focus views in the new shell. Third, build the attention surface, which is the differentiator: the Agents list fed by the process scan, pane state and opt-in Claude Code hooks, treated as first-class on Windows and Linux. Fourth, add the MCP server over the app's own data. Fifth, admit optional widgets one at a time, each with its own smoke test: reader, GitHub monitor, Familiars, then local transcription. Sixth, ship publicly with signing and the updater. Structured ACP chat, a local utility model, third-party widgets, the notch and any form of computer use sit after that and each needs its own decision.

### Decisions only the owner can make

Six choices gate the work, and the research can inform but not settle them. The first is identity: a harness-neutral attention panel (this report's recommendation), a personal organiser with terminals, or a Coven client; the answer decides whether Familiars is core or optional and how Open Sesame relates to `chat` and `coven-cave`. The second is sign-in: mandatory, as designed, or required only for account-backed features. The third is whether to restructure `dist/` during the cutover or after it. The fourth is the default widget set, which should come from what the owner actually uses each day, since no usage record exists. The fifth is licence and business model: the local clone at HEAD has no licence file and `package.json` declares none, yet OpenAI's plan-usage route is published for open-source, locally hosted apps and a paid or hosted tier moves an app to a different path, and the market evidence says local features are expected to be free with revenue, if any, from sync, mobile or team services. The sixth is Linux packaging: AppImage is the only format the Tauri updater updates but has the weakest desktop integration, while deb, rpm or Flatpak integrate better and update through the package manager, and a Flatpak sandbox conflicts with host shells and CLIs unless broad permissions are granted (researchers' inference).

### What remains unverified

The researchers were explicit about the limits of their work, and those limits carry into every recommendation above. On the product: the app was never run, the repository clone was shallow, GitHub listing figures appeared stale, and open issues and pull requests were not read. On the market: no source measures demand for a widget-plus-agent desktop; many competitor facts come from vendor roundups that contradict each other (Nimbalyst's licensing, Sculptor's harness); the search for Windows and Linux agent-status tools was not exhaustive; and no published user research compares summon patterns. On Tauri: benchmarks are single-run or macOS-only; no benchmark compares channels with events; engine baselines for import maps and newer CSS on current WebKitGTK were not checked; which compositors implement the GlobalShortcuts portal, and whether Tauri exposes activation tokens for focusing a window on Wayland, were not confirmed; and the behaviour of `portable-pty` under ConPTY and of PATH-repair crates was not verified. On sign-in: WorkOS's current rules for loopback redirects and session lifetime were not retrieved, and the Warp case is the only market evidence on mandatory login. On harness policy: the vendors' terms documents themselves were not fetched, the Sign in with ChatGPT launch details rest on a secondary source, the exact current Claude Code version was unconfirmed, and several official Codex pages failed to load. On local models and computer use: many 2026 model names, prices and benchmark scores come from aggregators or vendors; sources disagree on some figures (Apple's on-device context size, OSWorld scores for the same models, which Claude plans include desktop computer use); and no production usage statistics for computer use were found.

## Conclusion

The restart's main risk is not Tauri, Rust or three operating systems; the plan handles those carefully. The risk is carrying the old breadth across intact. Every conflict this report raises with the written plan shares one root: the plan preserves contracts (the wire protocol, the all-method gate, an untouched `dist/`, verbatim error strings) as though there were users and data to protect, when the project's most valuable asset is that there are neither. With one user and no migration, the cheap moment to change the storage model, the streaming path, the window lifecycle, the bundle identifier and the sign-in rule is now, and each becomes expensive the day a second user installs the app. Reframing the work from porting features to admitting them, one at a time and only after each is seen working on three systems, is what converts nine days of unverified output into a product.

The landscape also suggests where durability lies. Orchestrator products were acquired, shut down or relaunched within a year, while the protocols underneath them (MCP, ACP, the vendors' own CLI streams) kept maturing, and vendor policy converged on one stable rule: the user runs the vendor's own binary and the app never holds a credential. An Open Sesame that owns very little (a window that appears instantly, a truthful list of who is waiting, the user's own notes and tasks served to any agent over MCP) depends on those stable layers and competes with almost nobody on Windows and Linux. Whether enough people want that combination is the one thing the research could not answer, and the walking skeleton is the cheapest way to find out.
