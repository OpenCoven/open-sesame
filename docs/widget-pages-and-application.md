# Widget pages and application workspace

New declarative widget packages use `schemaVersion: 2` and a required `page`: `focus`, `media`, `projects`, `console`, `reader`, `live` or `widgets`. Installation adds a separately named tab on that page. The package validator, editor schema, scaffold and three starters share the same contract. Existing v1 packages stay under Widgets; installation does not rewrite them or discard configuration, drafts or previous definitions. Replacing or rolling back a definition updates the destination without duplicating the instance. The Tools manager retains preview, export, configuration, replacement and removal.

Page tabs reuse the existing navigation and preserve mounted native panes, timers, PTYs, playback and drafts. Arrow keys, Home and End include both built-in and installed tabs. Widget content fills its page; unrelated capture controls are hidden while it is selected. Source loading and actions are explicit. Reads are bound to the selected instance and configuration, and are retired on edits, page changes, collapse, replacement, removal and handoff. Preview and installation never contact a provider or execute an action. Hidden pages remain hidden even when they retain a widget selection.

GitHub declares Projects as its destination. Choose Widgets → GitHub → Add to Projects to install and open its tab. Repository management is a compact disclosure; removing the widget preserves the private local repository registry. Five UX changes are a unified repository toolbar; Overview/PRs/Issues/Actions tabs with recent-item counts; local search, status filters and sorting; workflow/branch/event/relative-time context; and responsive cards/rows with preserved focus, safe links and explicit unavailable/empty/stale states. Lists are recent samples of up to eight PRs, eight issues and six runs, not repository totals. Issue sampling skips pull requests before applying its eight-issue bound. GitHub access remains GET-only through the existing local CLI account; no token is copied into the renderer and the widget cannot merge, rerun or edit GitHub content.

The pop-out uses its actual window canvas with an icon-only application header, fitted activity navigation when space permits, display controls, docking and fill-screen actions. It remains open when switching applications. The native window is freely resizable and can become the main application window, with standard close/minimize/resize controls and a Dock presence while detached. Its content and running sessions stay in the same web view. Escape or explicit close returns it to the compact widget without ending sessions. Keep open is directly accessible in the compact activity rail; in the application header the same preference controls Keep on top. The native display menu pins the docked widget and the detached application to the selected display UUID, handles disconnection and moves the application into that display's visible bounds without imposing the widget's aspect ratio.

Shared UI polish uses flat dark dialogs, consistent tab bars, inputs, button sizes, quiet borders and keyboard focus states. Reading’s add flow has concise Article/PDF, RSS and Website tabs, one primary action, a consistent URL field and optional Advanced options. The detached canvas no longer depends on stale preset pixel dimensions or a WebKit animation frame to follow a window resize.

Focused synthetic checks, the unified Mac verifier, hosted CI, rendered Safari fixtures, native compilation/signature, live providers and installed acceptance are separate evidence classes. Fixtures use synthetic GitHub metadata and do not send a model prompt, capture real user audio/screens or type a command into an existing shell. Actual display relocation, native Dock behavior and real provider behavior require direct installed acceptance.

See [optional widgets and lifecycle controls](widget-lifecycle.md) for activation, deactivation, uninstall, RSS defaults and saved-data behavior.

## Content-first controls

Reader uses at most three header rows including the application bar: application controls, collection navigation, and a single title/actions row. The title truncates without wrapping and retains its full tooltip; metadata shares that row when space permits. Read/save, speech and PDF options stay available in the article options menu. The content-focus icon beside the title or in the application controls opens a quiet content-only workspace on every page. Restore workspace or Escape returns the original layout; menus and dialogs receive Escape first. Content, player elements, editors and terminal sessions stay mounted, and focusing does not start playback, capture or a provider request.

Side-rail heading rows toggle their existing rails across Shells, machines, familiars, Reader, Projects and playlists. Add, search, sort and other explicit row actions keep their own targets and never toggle the rail as a side effect. Keyboard users can focus the full-row toggle.

The shared implementation is [content-focus.js](../dist/content-focus.js), [content-focus.css](../dist/content-focus.css) and [rail-headings.js](../dist/rail-headings.js). Run [the rendered interaction review](../scripts/review-content-focus.mjs) for header geometry, retained content, clipboard destination binding, row-action separation, familiar routing and fresh activation defaults.

## Shell selection and clipboard

The shell uses a solid, non-blinking block cursor when focused or unfocused. Select output and use Command-C/Command-V on macOS, Control-Shift-C/Control-Shift-V in the browser, or the terminal’s context menu for Copy selection, Paste, Select all and Copy all output. Ordinary Control-C remains a shell interrupt. Paste uses xterm’s bracketed-paste handling and rechecks the selected visible live pane after an asynchronous clipboard read. Copy/paste is plain text with a 1 MiB UTF-8 bound; the native receiver preserves the existing authenticated main-frame origin boundary and never reads clipboard text before an explicit action.
