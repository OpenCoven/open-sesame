# Optional widgets and installation

Open Widgets, select a catalog widget, then choose Install widget, Deactivate widget, Activate widget or Uninstall widget. Installation and account connection are separate: installing or activating does not sign in, send a prompt or start recording. The account setup controls are available only while the widget is active. Every catalog entry supports these controls, including GitHub, Coven Familiars, Spotify, Apple Music, YouTube, Claude Code, Codex and RSS & Atom.

RSS & Atom is optional on a fresh profile. Reader still opens saved bookmarks, articles and PDFs, while feed controls and the optional sample feed remain hidden until RSS is installed and active. Existing profiles with subscriptions retain RSS access during migration. No subscription or article is automatically deleted. GitHub also remains an optional installation; the other existing catalog integrations retain their previous availability until changed explicitly.

Inactive built-ins retain account settings and saved content. They reject new widget operations; feed responses and page reads that finish after deactivation cannot update their retired views. Music players are unloaded, GitHub polling is paused and running familiar replies receive cancellation requests. A Live CLI request already submitted to the host can finish there, but its result is discarded after deactivation. Reactivation does not resume a reply, recording or playback; reopen or reconnect explicitly. Uninstall removes the built-in installation state and its installed page entry, retaining subscriptions, articles, conversations, provider settings and credentials for an explicit reinstall. Signing out or deleting content remains a separate action in its existing owner UI.

Imported JSON widgets have the same active/inactive controls in Widgets → Manage tools. Inactive instances disappear from page tabs and launcher entries, retain saved configuration and unsaved drafts, and cannot start another live read. Reactivation restores the existing instance. Uninstall removes that instance's configuration, draft and replacement history after confirmation; independently saved Projects notes and bookmarks remain. Export its definition before uninstalling if you want to reinstall a package that is not bundled. Exported definitions exclude saved configuration and drafts. Pinning only controls manager expansion and remains separate from activation.

Pages such as Focus, Projects, Console, Reader, Live and Widgets are application navigation, and remain available when their optional integrations are inactive. Local files, saved documents, local transcript search and the Widgets management UI do not require an optional provider installation. Removing one provider does not remove an unrelated widget that uses an existing account through an approved capability.

## Implementation and regression entrypoints

[widget-lifecycle.js](../dist/widget-lifecycle.js) loads before feature scripts and owns built-in state in `open-sesame-widget-lifecycle-v1`. It migrates explicit legacy GitHub installation and existing Reader subscriptions without rewriting their content stores. Once written, explicit inactive/uninstalled state takes precedence over those legacy records. Invalid saved lifecycle data is preserved and fails closed; failed storage writes do not change runtime state. Account connection status must never be used as installation status. Changes dispatch `open-sesame-widgets-changed` only after storage succeeds. Storage events synchronize built-in and imported activation with separate browser pop-out documents, so docking does not restore a stale installation.

Imported activation belongs to the existing instance record in `open-sesame-tools-v1`; [tools-model.js](../dist/tools-model.js) restores legacy records as active, while [tools.js](../dist/tools.js) owns persistence, launcher filtering and read invalidation. [page-widgets.js](../dist/page-widgets.js) derives active entries and retires mounts when an instance is deactivated or removed. Keep these lifecycle boundaries intact when adding a catalog entry or provider operation; guard callable APIs as well as visible controls. A new catalog ID must also be registered in the built-in lifecycle model and covered by its tests.

Run `node scripts/check-widget-lifecycle.mjs`, `node scripts/check-tools-ui.mjs` and `node scripts/check-page-widgets.mjs`, then the normal [verification workflow](development-workflow.md#implement--verify--review). The regressions cover fresh defaults, migration, persistence, corrupt/full storage, saved content and draft preservation, pending read retirement, reactivation and uninstall. Browser fixtures, native compilation, hosted CI, installed app acceptance and live provider results remain separate evidence classes.
