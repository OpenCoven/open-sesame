# Tauri shell and new UI shell for the desktop restart

[open-sesame](src/lib.rs) is the Tauri 2 application of the restart in [epic #58](https://github.com/OpenCoven/open-sesame/issues/58): one window, a tray icon and one command. It is not shipped; the Swift host and Python bridge under [desktop](../desktop/AGENTS.md) remain the running application until the cutover. Read the root [instructions](../AGENTS.md) and the [core's instructions](../crates/AGENTS.md) first; the ownership, evidence, publication and prose rules there apply here.

The window label is not an isolation boundary. Any script in the main document can call the bridge, so the main window loads only this application's own files and no third-party script may ever be loaded there. The one reviewed exception to "this application's own files" is the terminal emulator described below, which is a bundled file from this repository and not a remote one. That rule is held in four places, and a change that loosens one needs a reviewed reason: the content security policy in [tauri.conf.json](tauri.conf.json) admits only bundled script; [the capability](capabilities/default.json) grants the main window alone and names no remote page; [window.rs](src/window.rs) refuses navigation away from the application's pages and refuses new windows; and [router.rs](src/router.rs) drops a request from any other window or page before the gate is even asked.

Terminal panes ([#74](https://github.com/OpenCoven/open-sesame/issues/74)) are split between the core and this crate. [The core's terminal module](../crates/core/src/terminal/mod.rs) owns the shell, the pseudo-terminal, the pacing and the kill; [terminal.rs](src/terminal.rs) here only joins a pane to a Tauri channel and holds the clipboard, and [project.rs](src/project.rs) holds the folder dialog and reveal. Output travels on one channel per pane as raw bytes, in order, followed by `terminal.exit`; it is never a window event. The page acknowledges what the emulator has parsed with `terminal.ack`, and the core stops reading from the shell when the page falls a megabyte behind, so a flood slows the program instead of filling memory. The clipboard, dialog and opener plugins are used from Rust only: the capability grants the page none of their commands, and it must stay that way. Panes belong to the page that opened them: when the main window starts to load a page, [window.rs](src/window.rs) calls `page_replaced` in [terminal.rs](src/terminal.rs), which takes every pane off the list and has another thread end their processes, so the window's thread waits only for the pane list, because the new page can neither show nor close them ([#112](https://github.com/OpenCoven/open-sesame/issues/112)). The one exception is a system that refuses the thread: then the window's thread ends the panes itself, late rather than never. The close covers a page that loads again and nothing else: where the web content process ends and nothing reloads the page, which is so on Linux and Windows, and for a `terminal.open` from the old page that is handled after the close, panes still run until Quit. Keep that call out of any development-only block, whatever encloses it. [check-tauri-terminal.mjs](../scripts/check-tauri-terminal.mjs) reads text, and its comment lists what it reads; it does not read what encloses the statement, the match or the function, so it does not refuse a handler made development-only from outside. The self-test's reload pass shows the call running in a development build, the only kind it runs in. Nothing in the repository shows it for a release build; that is for a reviewer to read.

The emulator is the reviewed xterm.js bundle in [dist/vendor](../dist/vendor/THIRD-PARTY.txt). It is not copied: `frontendDist` in [tauri.conf.json](tauri.conf.json) lists `../ui` and the two emulator files, so the application serves them as `./xterm.js` and `./xterm.css` beside the shell. Do not add a file of either name to `ui/`, and do not add another entry to that list without review, because every listed file becomes loadable by the main window. The emulator writes cell colours as style attributes, so the policy's `style-src` is `'self' 'unsafe-inline'`; `script-src` stays `'self'` and [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) fails if `unsafe` appears anywhere else. Only the DOM renderer is bundled, so there is no renderer toggle.

A development build started with the `OPEN_SESAME_SELFTEST` environment variable set to a JSON object runs [ui/dev/selftest.js](../ui/dev/selftest.js), the launched-app acceptance pass for panes: a marker through the default shell, a folder with spaces and non-ASCII characters, three characters whose bytes arrive in two messages each and must be drawn whole, a flood of numbered lines checked byte by byte while timer and frame gaps are recorded, a pane closed over a long-running child, and three panes left open for Quit. The gaps are recorded and not judged: no limit for them has been set, so the flood step is not evidence that the window stayed responsive. With `"reload": true` in the request it runs a short separate pass instead: two panes with long-running children, the page loaded again, and a check from the new page that the old page's processes are gone. It writes its report through a shell to the file named by `out`, and the script that started the app reads it, quits the app and checks that every recorded process is gone. A release build never sets the flag ([window.rs](src/window.rs)). A development build that finds the variable set to anything other than a JSON object, an empty value included, says so on standard error and runs no self-test. On macOS, an app started from the desktop may not read files in Documents, Desktop or Downloads, so a script inside a bundle that reads the request from such a folder sets the variable to nothing ([#141](https://github.com/OpenCoven/open-sesame/issues/141)); write the request into the script, or read it from a folder outside those three. `ui/dev/selftest.js` is still bundled with a release build, where nothing loads it; the owner left that as it is on 16 November 2026 until [#87](https://github.com/OpenCoven/open-sesame/issues/87) and [#88](https://github.com/OpenCoven/open-sesame/issues/88) decide it when they set up release packaging, so do not move, exclude or strip it before then. The window belongs to the test while it runs: closing a tab by hand breaks the run, and such a run is not evidence.

[bridge_request](src/router.rs) is the only command. Do not add a second one: a new feature is a method on the wire protocol, admitted in the core's gate by the change that ports its handler. The command runs [gate::dispatch](../crates/core/src/gate.rs) first and then routes the allowed request to sign-in, to the window methods in [window.rs](src/window.rs), or to [Core::handle](../crates/core/src/handler.rs). [build.rs](build.rs) declares the command so that Tauri refuses it for any window the capability does not name. For a Windows build it also has the linker embed the application manifest in everything the package links and leaves Tauri's own copy out: Tauri's copy reaches the application binary only, and the library's test program does not start without one.

The main window is created in Rust in [window.rs](src/window.rs), not in the configuration, so the initialisation script sets `window.__OPEN_SESAME_NATIVE__`, `window.__OPEN_SESAME_VERSION__`, `window.__OPEN_SESAME_PRESENTATION__` and `window.__OPEN_SESAME_SURFACE__` before any page script runs. Closing the window hides it and keeps the page alive; the page must not load again when the window is shown. Quit is the tray's explicit action, and every way out ends in `RunEvent::Exit` in [lib.rs](src/lib.rs), which shuts the core down. The [tray](src/tray.rs) menu works everywhere; Tauri's tray emits no click events on Linux, so nothing may depend on a click there.

On macOS, Windows, X11 and Wayland sessions with the layer-shell protocol that window is the companion rail, [rail.rs](src/rail.rs), described in the [rail contract](../docs/companion-rail.md): one frameless window above the others that rests against a screen edge as a strip of icons on the display the pointer is on, and opens into the panel beside the strip. The window is never shown or hidden to summon it; it changes size. `rail.rs` is the only code that places it, and it does so from one thread that asks for the pointer and the displays on the main thread, with the decisions (`decide`, `frame`) kept as plain functions that `cargo test` covers without a window. Every way of summoning in the next paragraphs ends in `window::toggle`, `toggle_at`, `toggle_from_tray_menu`, `show` or `hide`, which hand over to the rail first: the shortcut, `open-sesame --toggle`, a second launch, the Dock and on Windows a click on the tray icon reach `rail::toggle`, `open` and `collapse`, which open the panel to stay and give it the keyboard, and the same again closes it to the strip and gives the keyboard back; the tray's menu item reaches `rail::toggle_shown` through `window::toggle_from_tray_menu`, and takes the whole rail off the screen and puts the strip back. Those rail functions answer with the `summon::Press` they made, `Show` or `Hide`, never `Forward`. Whether a press on an open panel that has lost the keyboard should take the keyboard back instead of closing it is an open question for the owner on [#161](https://github.com/OpenCoven/open-sesame/issues/161); today it closes. A pointer that rests on the strip opens the panel without the keyboard until the pointer leaves; a panel opened that way and then clicked closes when it loses the keyboard, whatever the hide-on-blur setting says, unless something holds the window. The page learns the state from `rail.status` and the `rail.changed` host message and changes it with `rail.set`, both in the gate; it never sizes or moves the window. Keep the strip's size in `rail.rs` equal to the page's (`--rail-width` and `--rail-height` in [tokens.css](../ui/tokens.css)); [check-ui-rail.mjs](../scripts/check-ui-rail.mjs) fails when they differ. On macOS the rail works in points and sets the frame through AppKit, because Tauri reports each display in its own scale; elsewhere it works in physical pixels. Outside macOS the strip is a window that refuses the keyboard (`set_focusable(false)`), so a click on it does not take the keyboard from the application a person is typing in, and closing a panel that had the keyboard takes the window off the screen for a moment so the system gives the keyboard back. A Wayland session cannot place a window, so there the rail is a layer surface where the compositor has the layer-shell protocol (KDE, Sway, Hyprland; not GNOME): [layer.rs](src/layer.rs) opens `libgtk-layer-shell` with `dlopen` when it is installed, never links it, and turns the GTK window into a surface docked against the edge before the window is first shown. The session picks the output and says only whether the pointer is over the rail, so `rail.rs` decides against one stand-in display, the strip does not follow the pointer, and a panel a command opens is taken off the screen and shown again so that it comes up on the output in use. The keyboard there is a mode the surface asks for: none for the strip, on demand for a peek, and exclusive for a panel opened to stay until the pointer has been over it and left (`rail::loosen`), because a session gives a layer surface the keyboard in no other way without a click. Without the library or the protocol, or with `OPEN_SESAME_LAYER_SHELL=off`, `rail::presentation` answers the ordinary window: no pointer thread starts and `rail.set` answers with the gate's not-on-this-system sentence. Keep every gtk-layer-shell call in `layer.rs` and on the main thread, and do not link the library: an application linked against it does not start where it is missing. A report that the window lost the keyboard is acted on only when the rail thought it had it (`rail::focus_changed`), because a session may repeat it. The window's material (a vibrancy view on macOS, Mica on Windows 11) is asked for in `rail::shape` and needs Tauri's `macos-private-api` feature, which makes the web view see-through; `OPEN_SESAME_MATERIAL=off` gives a solid page in any build. A development build reads `OPEN_SESAME_PRESENTATION=window` to show the ordinary window on any system and `OPEN_SESAME_DEV_POINTER`, a file holding `x y`, as a stand-in for the pointer, so a launched-app check can place the rail on each display of a shared machine without moving anyone's pointer; a release build reads neither. The edge and whether a resting pointer opens the panel are kept in `rail.json` beside the summon settings, under the same rule: in memory in a release build, in the folder named by `OPEN_SESAME_DEV_CONFIG_DIR` in a development build. Two things are particular to Windows, both found by the first start there: a window with a shadow and no frame keeps an unseen border, so `place` takes it off the position, and the window's focus events follow the web view and not the front window, so `has_keyboard` asks Windows which window is in front. The hosted Rust job starts the built binary on the Windows runner and checks both ([rail-windows.ps1](../scripts/fixtures/rail-windows.ps1)); extend that check when the Windows path changes.

Summon is [summon.rs](src/summon.rs), from [#71](https://github.com/OpenCoven/open-sesame/issues/71): the ways to make the window appear from anywhere. The baseline works on every system: the tray menu, launching the application again, and `open-sesame --toggle`. `tauri-plugin-single-instance` must stay the first plugin registered in [lib.rs](src/lib.rs), so a second process hands its arguments to the running one and exits before it creates a window; without a D-Bus session bus on Linux the plugin does nothing and a second launch is a second application. On macOS, Windows and X11 a global shortcut does the same as `--toggle`, with one difference: when hide-on-blur has just hidden the window because the press itself took the keyboard, the shortcut and the click on the Windows tray icon do nothing more, and `--toggle` and the tray's menu item are not held back that way. It is registered from Rust through `tauri-plugin-global-shortcut`, and the capability grants the page none of that plugin's commands: the page asks through `summon.status`, `summon.setShortcut`, `summon.setHideOnBlur` and `summon.hold`, which are in the gate like any other method. A shortcut needs a modifier, and it must not be something a person presses while writing, because registering it takes that from every application ([#115](https://github.com/OpenCoven/open-sesame/issues/115), decided on 16 November 2026). Shift alone is enough only for a function key or a media or volume key; with any other key it is refused: the keys that type, and also the arrows, Home, End, Page Up, Page Down, Backspace, Delete, Insert, Escape, Pause, Print Screen and the lock keys. A letter is refused with Option, with Shift or without, on a Mac, and with Control+Alt on Windows, which is how the right-hand Alt of many keyboards (AltGr) is reported. Each of the two is refused only on the system where it types, so a settings file carried from one system to another can hold a shortcut the other refuses; on Linux neither is refused, because AltGr there is a modifier a shortcut cannot name. A digit or a punctuation key with Option or AltGr types a character too and is still accepted: the decision names letters. Each refusal has its own sentence (`SHIFT_ALONE`, `OPTION_WITH_A_LETTER`, `ALT_GR_WITH_A_LETTER`), so a person who held Shift is no longer told to hold Shift; the three were written for this change and wait for the owner's reading. The Shift sentence suggests Control or Command and not Alt, because on a Mac Alt and Shift with a letter is refused in turn. A saved shortcut the rules no longer take is replaced by the default, and `summon.status` then carries a `notice` that says which one it was, for the rest of that run or until the person sets a shortcut, or none, themselves; the page shows it as a warning in front of the status sentence, except on Wayland, where no shortcut is registered and the page says only how to bind the command. Only a saved key combination with a modifier is announced: a key by itself was never taken, and text in the file that never was a key combination is a damaged file; both are replaced without a word. It is said again at the next start only while the file still holds the refused shortcut, and saving either setting writes the default over it. What the file held is repeated only when it is at most 64 printable ASCII characters. A refused registration is kept and returned, never swallowed, and a refused change puts the previous shortcut back. macOS accepts a shortcut another application already holds, so a conflict cannot be detected there; X11 and Windows refuse it. The default, `Control+Alt+Shift+Space`, holds three modifiers because every pair of them with Space is already some launcher's, password manager's or system's own: Alt+Space is ChatGPT's, Gemini's, Raycast's, Alfred's and the Swift host's, and Gemini's Mac app also takes Option+Shift+Space. Changing it is the owner's call.

This paragraph is the ordinary window's; the rail answers a press first (above) and is never behind another window. One press is the shortcut, `open-sesame --toggle`, the tray's menu item or, on Windows, a click on the tray icon (decided on 16 November 2026 for #115): a hidden or minimized window is shown, a window that is open but behind comes to the front, and a window in front hides. The shortcut, `--toggle` and the click follow [summon::press](src/summon.rs); the tray's menu item has the same three outcomes and its own rule for "in front", `summon::tray_item`, described below. Before, every press hid a window that was open, whether or not the person could see it; do not go back to that. "In front" means the window has the keyboard now, or lost it less than `BLUR_GRACE` (300 ms) ago. The second half is there because some presses take the keyboard before they are reported: the key grab on X11, and by reasoning the taskbar on Windows. Its cost is that a person who turns to another application and presses within that third of a second hides the window. The tray's menu item cannot ask the window at the moment it is chosen, because the open menu may have had the keyboard for any length of time. Where the press that opens the menu is reported, which is macOS for either button and Windows for the right one (`summon::opens_the_tray_menu`), [tray.rs](src/tray.rs) notes what the window was doing then and the item goes by that for up to a minute. Nothing says when a menu was dismissed without a choice, so a note that old can still decide for a menu opened later without a press. Where it is not, which is Linux, a window that lost the keyboard less than ten seconds ago counts as in front (`TRAY_MENU_GRACE`); that number is a guess, and its cost in both directions is written on the constant. What has been seen is one thing only: a development build at `86dbeb9` in a Linux container, on X11 under Xvfb and Openbox, went show, forward, hide in that order for the shortcut, for `--toggle` and for the tray's item chosen over D-Bus, and the item hid the window two seconds into a keyboard grab and brought it forward twelve seconds into one. A container is not a desktop session. Nothing of this has been seen on macOS, on Windows, on Wayland or with a real panel, and each system's meaning of in front is to be checked in [#78](https://github.com/OpenCoven/open-sesame/issues/78).

On Wayland an application cannot grab a key. [summon::session](src/summon.rs) decides the kind of session once, nothing is registered, the window is not positioned, `window.keepOpen` answers with the gate's not-on-this-system sentence, and the page names the command to bind in the desktop's own keyboard settings. Do not add a call that moves the window or forces it on top without a check for the session. The docked rail is not such a call: the session places a layer surface, and [layer.rs](src/layer.rs) only asks. The GlobalShortcuts portal is not used yet; [#108](https://github.com/OpenCoven/open-sesame/issues/108) owns it.

On macOS [panel.rs](src/panel.rs) turns the window into a panel with `tauri-nspanel`, so it takes the keyboard without activating the application and can appear on the Space in front, a full-screen one included. The panel crate's calls go straight to AppKit, which ends the process when a window is ordered from another thread; Tauri's own window calls are dispatched for you and these are not, so every one outside `setup` goes through `run_on_main_thread`. Do not show the panel with the crate's `show_and_make_key`: it asks for the panel's content view as the first responder, the content view refuses, and AppKit makes the window itself the first responder, which takes the keyboard from the web view, so what was typed after the shortcut reached nothing ([#142](https://github.com/OpenCoven/open-sesame/issues/142)). [panel::show](src/panel.rs) orders the panel in front, makes it key and then focuses the web view; in a launched app on macOS, with synthetic input, that gave the keyboard back to the shell input the page had focused. A person's real keyboard is the check that remains, in #78. On Windows a left click on the tray icon is one press, and a hidden window is first placed against the icon inside the screen's work area ([summon::popover_position](src/summon.rs)); a window that is open is brought forward or hidden where it is. A right click opens the menu; elsewhere a click only opens the menu. Where the window is the rail, a left click opens or closes the rail's panel instead, and the rail keeps its own place.

The page never opens the web view's native context menu ([#115](https://github.com/OpenCoven/open-sesame/issues/115), decided on 16 November 2026), because that menu is another window and opening it can take the keyboard from a window that hides when it loses focus. [context-menu.js](../ui/context-menu.js) cancels every `contextmenu` event, listening in the capture phase so that no part of the page can let the native menu through, and draws a menu in the page where there is something to offer, once the event has bubbled back to the document, so that the part of the page that was pressed has heard it first (the terminal emulator selects the word under the pointer in its own listener on a Mac): Cut, Copy, Paste and Select All in a text field, Copy for selected text, and for a part of the page that calls `provideMenu` whatever that part gives, as a terminal pane gives Copy and Paste. Copy and paste go through `terminal.clipboard.read` and `terminal.clipboard.write`, the only clipboard access the host gives the page (the palette copies an answer with the web view's own `navigator.clipboard`, which this does not reach); a field that hides what is typed gives nothing to the clipboard. Not covered: a `<select>` list and an input method's window are native popups too and still need a rule per system, and the default views have such lists (Today's capture kind, Projects' filters, kind and the editor's project); a field that is `contenteditable` or has no text selection (email, number) gets no field menu, only Copy when text is selected on the page, which is offered wherever the menu is asked for; the menu is the page's from the moment [main.js](../ui/main.js) runs, so a page whose script failed to load has the native one; a paste made from the menu is not a step of the field's own undo; and a development build no longer offers Inspect Element on a right click. Seen in the same container with hide-on-blur on: before this change a right click in the shortcut field hid the window, and with it the window stays, the menu is drawn, and Cut and Paste from it changed what the field then saved. The menu has not been seen on macOS or on Windows.

Hide-on-blur is a setting that is off unless the person turns it on; for the rail, hiding means closing the panel to the strip. A feature that takes the focus away on purpose must take [summon::hold](src/summon.rs) first and keep the value until it is done: a native dialog, as the folder dialog in [project.rs](src/project.rs) does, or a browser sign-in. The page reports a drag with `summon.hold`, and a pinned window stays. `summon.hold` takes an optional `reason`, a short lower-case name, and the host keeps the page's holds by reason, so the end of a drag does not release a hold the page took for something else; a request with no reason is the drag, which is the only reason the page sends today. The reasons are a set, not a count: one taken twice is released once. At most eight named reasons are held at once and one more is refused; the drag is beside that limit and never refused, because the page's drag script does not look at the answer. When the window starts to load a page, [window.rs](src/window.rs) calls `summon::page_replaced`, which releases every hold the page has taken so far, because the page that took them is gone; the holds features take and the pin stay. Two cases it does not reach: a request is not tied to the page that sent it, so a `summon.hold` from the old page that is handled after the load is kept until something releases that reason (for the drag, the end of the next drag that starts in the page) or the next page load; and a page whose web content process ends without a reload starts no page load, so its holds stay. Keep that call out of any development-only block, whatever encloses it. [check-tauri-summon.mjs](../scripts/check-tauri-summon.mjs) reads text, and its comment lists what it reads (the call [#112](https://github.com/OpenCoven/open-sesame/issues/112) added to the same arm stands after it, where the check does not read); it does not read what encloses the statement, the match or the function, so it does not refuse a hook made development-only from outside. Nothing in the repository shows a page load releasing holds in any build; that is for a reviewer to read and for a launched window to show. In a release build the shortcut and this setting are kept in memory only: [#105](https://github.com/OpenCoven/open-sesame/issues/105) gives the core's storage a restart data folder ([data.rs](src/data.rs)), but these settings are not wired to it yet. A development build keeps them in the folder named by `OPEN_SESAME_DEV_CONFIG_DIR`, which a launched-app check uses so that it never writes into a person's home folder.

Sign-in is [auth.rs](src/auth.rs), from [#72](https://github.com/OpenCoven/open-sesame/issues/72): it gives the core's sign-in logic ([crates/core/src/auth](../crates/core/src/auth/mod.rs)) the network calls, the saved credential, a browser and the callback. It is an account control and not a door, as decided in [#60](https://github.com/OpenCoven/open-sesame/issues/60): the window opens in the shell, no method in the gate needs a session, and a refresh that cannot reach the server is tried again later without locking anything. Do not make a local feature wait for a session. The browser is opened from Rust only, through the opener crate's function, and only for an address on the WorkOS API origin ([auth::may_open](src/auth.rs)); the opener plugin is registered for the file manager of #74, and the page is granted no command of it or of the deep-link plugin, so the page cannot open an address or register a scheme. The page learns the status from `auth.status` and from the `auth.changed` host message, which carry no address, code or credential. No link travels as an event ([#116](https://github.com/OpenCoven/open-sesame/issues/116)): Tauri sends an event to every page listener as well as to Rust, the main window may listen for events because host messages reach it that way, and Tauri cannot narrow `core:event:allow-listen` to some event names, so a link announced as the deep-link plugin's `deep-link://new-url` event would give any script in the page the callback's code and `state`. So the single-instance plugin is built without its `deep-link` feature, nothing calls `on_open_url`, and the deep-link plugin is registered only in a development build on Windows and Linux, to register the scheme; there it announces a link only while it starts, before any page exists. Keep all three; [check-tauri-sign-in.mjs](../scripts/check-tauri-sign-in.mjs) pins them by reading the source. The tests in [link.rs](src/link.rs) show only that taking a link announces nothing by itself: they run in an application without the plugin, so they cannot tell whether the real one registers it. The code in a link is still of no use without the verifier, which never leaves the host.

The callback arrives on the `opensesame` scheme named in [tauri.conf.json](tauri.conf.json), whose `plugins.deep-link` entry is also what the bundler reads to register the scheme, and [link.rs](src/link.rs) gives it to sign-in. On macOS the system hands it to the running application as `RunEvent::Opened`. On Windows and Linux it starts a second process with the link as its only argument; the single-instance plugin hands that process's arguments to the running application before the process exits, which is one more reason the plugin stays first, and `link::handed_over` takes the link out of them before summon sees them. Only sign-in's two links are taken this way, the callback and the address that says the remote session ended. Any other address on the scheme is someone asking for the application, as the hosted login page's "Open Open Sesame" (`opensesame://auth/login`) is: a launch with it is an ordinary launch, and a second launch with it is left to summon, which shows the window. On macOS the system hands such an address to the running application, which ignores it, as it always has; whether the system's own activation shows a hidden window there has not been checked. The address does not start a sign-in in this application. A launch that carries only one of sign-in's links and was not handed over exits at the top of `setup`, before `setup` opens storage, starts anything or creates a window: either nothing is running, or the session is a Linux one with no D-Bus session bus, where the single-instance plugin cannot find the running application. That check stays the first thing in `setup`, because a launch that ends there manages no state and the exit handler would shut nothing down. The plugins' own setups have run by then: single-instance has claimed the instance, and in a development build on Windows and Linux the deep-link plugin has announced the link, with no page to hear it. A link is taken as the address parser returns it, not as it arrived: the parser puts the scheme in lower case, drops spaces and control characters around the address and tabs and line ends inside it, works out `.` and `..` in the path, and drops an empty user name and an empty port, so `opensesame://auth/x/../callback` and `opensesame://@auth/callback` are the callback too, as they were for the deep-link plugin. A path that only looks like one of the two, `auth/callback/` with a slash after it or `AUTH/callback`, is not. The core sends a code to the server only when the callback passes every rule, and only a callback that carries the waiting attempt's `state` can end that attempt, so a link sent by another program, or an earlier attempt's callback, signs nobody in and leaves a waiting sign-in waiting ([#116](https://github.com/OpenCoven/open-sesame/issues/116)); this is how the Swift host behaved, where only the browser session's own callback reached the attempt. A callback that carries the state and no usable code, as a refusal in the browser does, ends the attempt with a sentence that is not about the connection. In a development build on Windows and Linux the scheme is registered at start for the current user, in the registry on Windows and as a handler file with a line in `mimeapps.list` on Linux, and removed again when that run exits cleanly ([#132](https://github.com/OpenCoven/open-sesame/issues/132), `link::unregister`): on Windows only the current user's key `HKEY_CURRENT_USER\Software\Classes\opensesame`, and only while its command still names this executable, so an all-users key (Tauri's MSI installer writes one) and a key another build wrote since are left, while Tauri's NSIS installer in its default per-user mode writes this same key, which a development run overwrites and its clean exit then removes, leaving the installed build with no registration until it is reinstalled ([#220](https://github.com/OpenCoven/open-sesame/issues/220)); on Linux the deep-link plugin's `unregister`, which takes this program's handler out of `mimeapps.list` and out of its handler file and refreshes the desktop database. A launch that only carried a link and ended at the top of `setup` registered nothing and removes nothing. A build that was killed leaves its registration, so a link that arrives when no development build is running starts the development binary, which then exits without a window; to remove it by hand, on Windows delete that key, and on Linux delete `~/.local/share/applications/open-sesame-handler.desktop` and its line in `~/.config/mimeapps.list`; on Linux that registration is the plugin's handler file, whose `Exec` path is quoted, and `xdg-open` from xdg-utils 1.1.3 cannot run it on a session with no desktop integration, where `gio open` can; on macOS only an installed bundle owns a scheme, so a development build there never receives a callback, and a bundle that registers the scheme must not be built or launched on a machine where the installed Swift app owns it until [#87](https://github.com/OpenCoven/open-sesame/issues/87) settles the identifier. The [Mac preview](../docs/mac-preview.md) is the exception that proves the rule: [preview.conf.json](preview.conf.json) gives it its own identifier and name and registers no scheme, so it can sit beside the Swift app and has no sign-in.

The refresh token is kept only by the system: Keychain and Windows Credential Manager through the `keyring` crate, and on Linux the Secret Service through that crate's own store, opened directly, under a service name that differs from the installed Swift app's because a refresh token is replaced each time it is used. On Linux with no Secret Service, sign-in is refused before the browser opens with a sentence that says what to install and to try again; a keyring that is there but locked gets the sentence about unlocking instead. The `keyring` crate opens the store once for as long as the application runs and keeps a failure too, so on Linux the Secret Service store is held by `Reopening` in [auth.rs](src/auth.rs) instead ([#116](https://github.com/OpenCoven/open-sesame/issues/116)): it is opened when first asked, opened again on the next ask if that failed, and when a store that was open answers with a platform failure, as after the keyring service restarts, it is opened again and asked once more. A locked keyring or a dismissed unlock prompt answers "no access" and is never asked twice, and there is no other place a sign-in is written when the store cannot be reached; keep both. The reopening and the single ask were measured with gnome-keyring 46.1 in a container, with no other Secret Service, and with a stand-in program in place of the unlock dialog: no real dialog was shown. Two cases it does not reach ([#130](https://github.com/OpenCoven/open-sesame/issues/130)): a keyring that was just installed and has no default collection passes the look and then refuses the save, after the browser; and a keyring that dies while its unlock prompt is open leaves the call waiting, because the library waits for a prompt with no limit. The two tests that start and stop a real keyring are ignored, run by hand in a disposable container only, and refuse to run without `OPEN_SESAME_DISPOSABLE_KEYRING=1`, because they end the user's keyring service. The page still gives `auth.signIn` three minutes instead of fifteen seconds (`LIMITS` in [bridge.js](../ui/bridge.js)). That was for the read of the saved sign-in, which on a locked keyring waits for the unlock prompt; since #130 the request no longer waits for that read, so nothing needs the longer limit, and it is left as it is. Never ask the store on the main thread: a locked keyring answers only after its unlock prompt, so the restore at launch asks it on its own thread and the window does not wait. Nor may a request from the page wait for it ([#130](https://github.com/OpenCoven/open-sesame/issues/130)): the page gives a request fifteen seconds and then says the connection was lost, and a person may leave the prompt open for minutes. So in [auth.rs](src/auth.rs) the look before Sign in is made on a thread of its own, one at a time, and waited for two seconds. An answer that comes after its press was refused is kept for thirty seconds and is the next press's answer, once, so a store that is always slower than two seconds still lets a person sign in on the second press; a look that has not answered after two minutes is given up and the next press asks again on a new thread, and what a look given up answers after that new look was made is dropped; an old look that answers before any further press is kept the same thirty seconds. Before it looks, Sign in asks the controller whether the store is held up (`store_busy`: a call waited for past two seconds, or one given up and still out), and is refused without the store being asked if so. Cancel uses the controller's `cancel_now`. Sign out runs on a thread of its own and the request is answered as soon as that thread says how it began: refused, with nothing changed, or begun, which is when the person is signed out here and before the store is asked. The address that ends the remote session is opened then, not after the removal, and the status says the rest: the keychain being waited for, then how the removal ended. A press that finds the store being waited for is refused with `KEYCHAIN_WAITING` and changes nothing; for Sign in that includes not asking the store, while the status says the keychain is being waited for and while a call given up is still out, and the controller's own read at launch counts as such a wait. The question asked before that read on Linux, described next, is not the controller's and is not counted: the status does not say the keychain is being waited for then, and a press of Sign in makes a look. [check-tauri-sign-in.mjs](../scripts/check-tauri-sign-in.mjs) reads the file as text for this, so it holds spellings and not behaviour: that the store question and the controller's waiting `cancel` and `sign_out`, as they would be written on the calling thread, do not occur outside the tests; the shape of the look, of Cancel and of Sign out; and that three times the two seconds, which is the most Sign in waits (the look, the state, and the host's own cancel when the browser will not open), stays below the fifteen seconds the page gives a request by default, the shortest it gives any; Sign in has three minutes of its own there, so the comparison is stricter than Sign in needs. The same call written another way passes it; the Rust tests hold the behaviour. It does not read what the controller does behind its three answering forms, which the core's tests hold, nor the fallback in `sign_out` for when no thread can be started, which waits as long as the store does. No host test has a signed-in session, so that Sign out passes the address on and that the thread left to cancel does cancel are held by that text only; and that thread cancels whatever sign-in is pending when the store lets it, which may be one begun after it. The sentences and the times are proposals in the pull request for #130. What this does not reach: a keyring that was installed and never set up still passes the look and refuses the save after the browser. A store call of the controller's that never answers, as with a keyring that dies while its prompt is open, is given up after two minutes; until that call returns, which may be never, the controller makes no store call and begins no sign-in, so Sign in is refused with the keychain sentence until then or until the application restarts, and each look given up leaves its thread behind. The read at launch on Linux, which asks whether the keyring can be reached before the restore, has no limit: it runs on its own thread and nothing waits for it, but a look made while it waits is refused as above. Nothing in [auth.rs](src/auth.rs) may print or log: an address carries the `state` and an answer carries tokens. The signed-out flag, which matters only when a credential could not be deleted, is kept in memory in a release build for the reason the summon settings are ([#105](https://github.com/OpenCoven/open-sesame/issues/105)). A real sign-in needs a person and an account; the tests use a stand-in server on a loopback port and never contact WorkOS, apart from one ignored test that asks for the public signing keys. A development build started with `OPEN_SESAME_DEV_AUTH_API` set to a loopback address talks to such a stand-in, which is how a launched build is checked without an account; a release build never reads it.

The new UI shell is [ui/](../ui/index.html), chosen in [#61](https://github.com/OpenCoven/open-sesame/issues/61) in place of carrying `dist/` over. It is framework-free ES modules with relative imports, no build step and no npm runtime dependency, and it shares no global between modules. [bridge.js](../ui/bridge.js) is the transport: it uses the global `window.__TAURI__` object, sends `{requestId, method, params}` through the command and hands host events to subscribers. The widget manifest, lazy lifetimes and JSON renderer live in `ui/`; read its [scoped instructions](../ui/AGENTS.md) and [contract](../docs/ui-shell.md). Downstream view/widget ports remain separate issues; do not edit `dist/` for the restart.

Host messages go out through [events.rs](src/events.rs), addressed to the main window. The address is not what keeps them there: Tauri delivers an event sent to one window to any page listener registered without a target, in whichever window it is, and that is the kind `listen` on the global object registers. Only the capability does, by granting event listening to the main window alone. Do not grant `core:event:allow-listen` to another window unless that window may read every host message; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) pins the capability's exact permissions and windows for this reason.

Run `npm run dev:app` to start the application from the bundled files, which is the path a release build uses and the one the security policy applies to. Plain `cargo tauri dev` also works: the Tauri CLI then serves `ui/` from a loopback address with its own reload script, which a development build accepts and a release build never does, and the content security policy is not applied on that path. Both need the Tauri CLI, installed once with `cargo install tauri-cli --locked`.

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root, then `npm run check`. The command's tests run on Tauri's windowless runtime and do not load the capability file; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) covers the transport against a fake window and reads the configuration, capability and shell files as text. Neither opens a window. A launched application is separate evidence, recorded per operating system: on macOS the tray menu cannot be opened by accessibility scripting, so hide, show and quit there are driven through the close button, the Dock icon and the application menu unless a person clicks the tray.

When wiring authentication, follow the core's [refresh recovery contract](../docs/auth-refresh-recovery.md). Keep the process alive until `AuthController::shutdown` returns on the host exit thread; it drains a running refresh through its credential-save attempt. Never call it reentrantly from a WorkOS API implementation or its change callback. The HTTP implementation must retain its 20-second timeout per request; an operating system keychain prompt can delay a store operation. Session verification remains separate from saving the rotated credential.

## Restart runtime ownership

[The data directory resolver](src/data.rs) uses the OS data root and the separate `org.opencoven.open-sesame.restart-development` namespace until #59/#87 settle production identity. `OPEN_SESAME_DEV_CONFIG_DIR` selects an absolute disposable qualification directory. Relative paths, parent traversal and existing symlink aliases into legacy data are refused. Protected roots include the identifier folder, `Open Sesame` under the OS data root and the actual native `Library/Application Support/Open Sesame` root, controller receipts under `.local/share/Open Sesame` and `.local/share/Perch`, and legacy lower-case data/state roots, including absolute `XDG_DATA_HOME/open-sesame`. The host supplies OS home/data roots; a relative legacy XDG data root is refused because its installed-data location cannot be established safely. Do not derive restart SQLite storage from the colliding bundle identifier or migrate installed Swift data. Opening runs on a background thread; pending storage requests return a still-opening sentence. Core accepts the result once, retains an opening failure as a plain storage error while other features remain available, and refuses late results after Quit. Shutdown drops an initialized SQLite connection. An opening thread blocked in an uninterruptible filesystem call is not joined on the UI thread and ends with the application process; no child process belongs to it. Case variants of the installed namespace are conservatively refused on macOS and Windows.

[Startup](src/startup.rs) owns one background login-shell capture. Requests may read the inherited snapshot while it is pending; no UI code may call the blocking `StartupEnv::get`. Quit cancels and joins capture before shutting down Core. The process runner must remain the sole collector of its own children (#97): do not install a global SIGCHLD reaper, call `wait(-1)` or otherwise collect runner-owned child statuses from the host. Terminal panes own their separate children through the terminal subsystem.

The [windowless bridge audit](src/router.rs) calls every admitted method with safe invalid input, exercising real handlers without opening dialogs or touching the clipboard. No admitted method is pending: with no sign-in running in the audit, the auth actions reach the router's sign-in branch, which answers that sign-in has not started, and a method admitted ahead of its handler must be listed with its issue. Unknown-method replies fail the audit. This is routing evidence; the actual-app storage, desktop-launch discovery and first-paint checks remain separate native acceptance.

For local native qualification, a debug-only `OPEN_SESAME_SELFTEST` object with `kind: "runtime"`, `phase: "save"` or `"list"`, a disposable marker `text` and optional `delayMs` loads [runtime-selftest.js](../ui/dev/runtime-selftest.js). It uses the actual page bridge and displays the saved/listed item or an error with `saved: false`. `OPEN_SESAME_RUNTIME_PROBE_DIR` opts into a fixed `runtime-fixture` lookup receipt from the actual AppState startup snapshot and Core override reader; it writes no environment values and starts no provider CLI. Probe work is queued on the blocking pool and never awaited by page-load or bridge callbacks. Each receipt preserves the observed event, process ID, sequence and environment source; per-observation files are retained, and an older completion cannot replace a newer latest receipt. These hooks neither add a renderer command nor run in a release build. Keep qualification folders outside protected user document locations and preserve the exact candidate identity and original failed attempts.
