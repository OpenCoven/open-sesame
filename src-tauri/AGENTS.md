# Tauri shell and new UI shell for the desktop restart

[open-sesame](src/lib.rs) is the Tauri 2 application of the restart in [epic #58](https://github.com/OpenCoven/open-sesame/issues/58): one window, a tray icon and one command. It is not shipped; the Swift host and Python bridge under [desktop](../desktop/AGENTS.md) remain the running application until the cutover. Read the root [instructions](../AGENTS.md) and the [core's instructions](../crates/AGENTS.md) first; the ownership, evidence, publication and prose rules there apply here.

The window label is not an isolation boundary. Any script in the main document can call the bridge, so the main window loads only this application's own files and no third-party script may ever be loaded there. The one reviewed exception to "this application's own files" is the terminal emulator described below, which is a bundled file from this repository and not a remote one. That rule is held in four places, and a change that loosens one needs a reviewed reason: the content security policy in [tauri.conf.json](tauri.conf.json) admits only bundled script; [the capability](capabilities/default.json) grants the main window alone and names no remote page; [window.rs](src/window.rs) refuses navigation away from the application's pages and refuses new windows; and [router.rs](src/router.rs) drops a request from any other window or page before the gate is even asked.

Terminal panes ([#74](https://github.com/OpenCoven/open-sesame/issues/74)) are split between the core and this crate. [The core's terminal module](../crates/core/src/terminal/mod.rs) owns the shell, the pseudo-terminal, the pacing and the kill; [terminal.rs](src/terminal.rs) here only joins a pane to a Tauri channel and holds the clipboard, and [project.rs](src/project.rs) holds the folder dialog and reveal. Output travels on one channel per pane as raw bytes, in order, followed by `terminal.exit`; it is never a window event. The page acknowledges what the emulator has parsed with `terminal.ack`, and the core stops reading from the shell when the page falls a megabyte behind, so a flood slows the program instead of filling memory. The clipboard, dialog and opener plugins are used from Rust only: the capability grants the page none of their commands, and it must stay that way. Panes belong to the page that opened them: when the main window starts to load a page, [window.rs](src/window.rs) calls `page_replaced` in [terminal.rs](src/terminal.rs), which takes every pane off the list and has another thread end their processes, so the window's thread waits only for the pane list, because the new page can neither show nor close them ([#112](https://github.com/OpenCoven/open-sesame/issues/112)). The one exception is a system that refuses the thread: then the window's thread ends the panes itself, late rather than never. The close covers a page that loads again and nothing else: where the web content process ends and nothing reloads the page, which is so on Linux and Windows, and for a `terminal.open` from the old page that is handled after the close, panes still run until Quit. Keep that call out of any development-only block, and before anything in its arm that is not a plain call; [check-tauri-terminal.mjs](../scripts/check-tauri-terminal.mjs) reads the source for that, for a single page-load handler, and for no attribute on its statement, on the arm or on `page_replaced`. It reads text and cannot show that the call runs.

The emulator is the reviewed xterm.js bundle in [dist/vendor](../dist/vendor/THIRD-PARTY.txt). It is not copied: `frontendDist` in [tauri.conf.json](tauri.conf.json) lists `../ui` and the two emulator files, so the application serves them as `./xterm.js` and `./xterm.css` beside the shell. Do not add a file of either name to `ui/`, and do not add another entry to that list without review, because every listed file becomes loadable by the main window. The emulator writes cell colours as style attributes, so the policy's `style-src` is `'self' 'unsafe-inline'`; `script-src` stays `'self'` and [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) fails if `unsafe` appears anywhere else. Only the DOM renderer is bundled, so there is no renderer toggle.

A development build started with the `OPEN_SESAME_SELFTEST` environment variable set to a JSON object runs [ui/dev/selftest.js](../ui/dev/selftest.js), the launched-app acceptance pass for panes: a marker through the default shell, a folder with spaces and non-ASCII characters, three characters whose bytes arrive in two messages each and must be drawn whole, a flood of numbered lines checked byte by byte while timer and frame gaps are recorded, a pane closed over a long-running child, and three panes left open for Quit. The gaps are recorded and not judged: no limit for them has been set, so the flood step is not evidence that the window stayed responsive. With `"reload": true` in the request it runs a short separate pass instead: two panes with long-running children, the page loaded again, and a check from the new page that the old page's processes are gone. It writes its report through a shell to the file named by `out`, and the script that started the app reads it, quits the app and checks that every recorded process is gone. A release build never sets the flag ([window.rs](src/window.rs)). The window belongs to the test while it runs: closing a tab by hand breaks the run, and such a run is not evidence.

[bridge_request](src/router.rs) is the only command. Do not add a second one: a new feature is a method on the wire protocol, admitted in the core's gate by the change that ports its handler. The command runs [gate::dispatch](../crates/core/src/gate.rs) first and then routes the allowed request to sign-in, to the window methods in [window.rs](src/window.rs), or to [Core::handle](../crates/core/src/handler.rs). [build.rs](build.rs) declares the command so that Tauri refuses it for any window the capability does not name. For a Windows build it also has the linker embed the application manifest in everything the package links and leaves Tauri's own copy out: Tauri's copy reaches the application binary only, and the library's test program does not start without one.

The main window is created in Rust in [window.rs](src/window.rs), not in the configuration, so the initialisation script sets `window.__OPEN_SESAME_NATIVE__` and `window.__OPEN_SESAME_VERSION__` before any page script runs. Closing the window hides it and keeps the page alive; the page must not load again when the window is shown. Quit is the tray's explicit action, and every way out ends in `RunEvent::Exit` in [lib.rs](src/lib.rs), which shuts the core down. The [tray](src/tray.rs) menu works everywhere; Tauri's tray emits no click events on Linux, so nothing may depend on a click there.

Summon is [summon.rs](src/summon.rs), from [#71](https://github.com/OpenCoven/open-sesame/issues/71): the ways to make the window appear from anywhere. The baseline works on every system: the tray menu, launching the application again, and `open-sesame --toggle`. `tauri-plugin-single-instance` must stay the first plugin registered in [lib.rs](src/lib.rs), so a second process hands its arguments to the running one and exits before it creates a window; without a D-Bus session bus on Linux the plugin does nothing and a second launch is a second application. On macOS, Windows and X11 a global shortcut toggles the window. It is registered from Rust through `tauri-plugin-global-shortcut`, and the capability grants the page none of that plugin's commands: the page asks through `summon.status`, `summon.setShortcut`, `summon.setHideOnBlur` and `summon.hold`, which are in the gate like any other method. A refused registration is kept and returned, never swallowed, and a refused change puts the previous shortcut back. macOS accepts a shortcut another application already holds, so a conflict cannot be detected there; X11 and Windows refuse it. The default, `Control+Alt+Shift+Space`, holds three modifiers because every pair of them with Space is already some launcher's, password manager's or system's own: Alt+Space is ChatGPT's, Gemini's, Raycast's, Alfred's and the Swift host's, and Gemini's Mac app also takes Option+Shift+Space. Changing it is the owner's call.

On Wayland an application cannot grab a key. [summon::session](src/summon.rs) decides the kind of session once, nothing is registered, the window is not positioned, `window.keepOpen` answers with the gate's not-on-this-system sentence, and the page names the command to bind in the desktop's own keyboard settings. Do not add a call that moves the window or forces it on top without a check for the session. The GlobalShortcuts portal is not used yet; [#108](https://github.com/OpenCoven/open-sesame/issues/108) owns it.

On macOS [panel.rs](src/panel.rs) turns the window into a panel with `tauri-nspanel`, so it takes the keyboard without activating the application and can appear on the Space in front, a full-screen one included. The panel crate's calls go straight to AppKit, which ends the process when a window is ordered from another thread; Tauri's own window calls are dispatched for you and these are not, so every one outside `setup` goes through `run_on_main_thread`. On Windows a left click on the tray icon places the window against the icon inside the screen's work area ([summon::popover_position](src/summon.rs)) and a right click opens the menu; elsewhere a click only opens the menu.

Hide-on-blur is a setting that is off unless the person turns it on. A feature that takes the focus away on purpose must take [summon::hold](src/summon.rs) first and keep the value until it is done: a native dialog, as the folder dialog in [project.rs](src/project.rs) does, or a browser sign-in. The page reports a drag with `summon.hold`, and a pinned window stays. In a release build the shortcut and this setting are kept in memory only: [#105](https://github.com/OpenCoven/open-sesame/issues/105) gives the core's storage a restart data folder ([data.rs](src/data.rs)), but these settings are not wired to it yet. A development build keeps them in the folder named by `OPEN_SESAME_DEV_CONFIG_DIR`, which a launched-app check uses so that it never writes into a person's home folder.

Sign-in is [auth.rs](src/auth.rs), from [#72](https://github.com/OpenCoven/open-sesame/issues/72): it gives the core's sign-in logic ([crates/core/src/auth](../crates/core/src/auth/mod.rs)) the network calls, the saved credential, a browser and the callback. It is an account control and not a door, as decided in [#60](https://github.com/OpenCoven/open-sesame/issues/60): the window opens in the shell, no method in the gate needs a session, and a refresh that cannot reach the server is tried again later without locking anything. Do not make a local feature wait for a session. The browser is opened from Rust only, through the opener crate's function, and only for an address on the WorkOS API origin ([auth::may_open](src/auth.rs)); the opener plugin is registered for the file manager of #74, and the page is granted no command of it or of the deep-link plugin, so the page cannot open an address or register a scheme. The page learns the status from `auth.status` and from the `auth.changed` host message, which carry no address, code or credential. The capability does not keep a link from the page: the deep-link plugin announces each link as its own `deep-link://new-url` event to every listener, and the main window may listen for events. The shell does not listen for it, and what keeps the link private is the rule that the main window loads only this application's own script; the code in a link is of no use without the verifier, which never leaves the host.

The callback arrives through `tauri-plugin-deep-link` on the `opensesame` scheme named in [tauri.conf.json](tauri.conf.json). On macOS the system hands it to the running application; on Windows and Linux it starts a second process, and the single-instance plugin's `deep-link` feature passes it to the running one before that process exits, which is one more reason the plugin stays first. A callback is given to the core exactly as it arrived, and the core sends a code to the server only when the callback carries the pending `state`. A link sent by another program therefore signs nobody in, but while a sign-in is waiting it ends that attempt, as any callback that fails the core's rules does. On a Linux session with no D-Bus session bus the single-instance plugin cannot find the running application, so a link there starts a second one with its own window. In a development build on Windows and Linux the scheme is registered at start for the current user and stays registered after the run ends, in the registry on Windows and as a handler file with a line in `mimeapps.list` on Linux; on Linux that registration is the plugin's handler file, whose `Exec` path is quoted, and `xdg-open` from xdg-utils 1.1.3 cannot run it on a session with no desktop integration, where `gio open` can; on macOS only an installed bundle owns a scheme, so a development build there never receives a callback, and a bundle must not be built or launched on a machine where the installed Swift app owns the scheme until [#87](https://github.com/OpenCoven/open-sesame/issues/87) settles the identifier.

The refresh token is kept only by the system: Keychain, Windows Credential Manager or the Secret Service, through the `keyring` crate, under a service name that differs from the installed Swift app's because a refresh token is replaced each time it is used. On Linux with no Secret Service, sign-in is refused before the browser opens with a sentence that says what to install and to start the application again, because the `keyring` crate opens the store once for as long as the application runs; a keyring that is there but locked gets the sentence about unlocking instead. Never ask the store on the main thread: a locked keyring answers only after its unlock prompt, so the restore at launch asks it on its own thread and the window does not wait. Nothing in [auth.rs](src/auth.rs) may print or log: an address carries the `state` and an answer carries tokens. The signed-out flag, which matters only when a credential could not be deleted, is kept in memory in a release build for the reason the summon settings are ([#105](https://github.com/OpenCoven/open-sesame/issues/105)). A real sign-in needs a person and an account; the tests use a stand-in server on a loopback port and never contact WorkOS, apart from one ignored test that asks for the public signing keys. A development build started with `OPEN_SESAME_DEV_AUTH_API` set to a loopback address talks to such a stand-in, which is how a launched build is checked without an account; a release build never reads it.

The new UI shell is [ui/](../ui/index.html), chosen in [#61](https://github.com/OpenCoven/open-sesame/issues/61) in place of carrying `dist/` over. It is framework-free ES modules with relative imports, no build step and no npm runtime dependency, and it shares no global between modules. [bridge.js](../ui/bridge.js) is the transport: it uses the global `window.__TAURI__` object, sends `{requestId, method, params}` through the command and hands host events to subscribers. The widget manifest, lazy lifetimes and JSON renderer live in `ui/`; read its [scoped instructions](../ui/AGENTS.md) and [contract](../docs/ui-shell.md). Downstream view/widget ports remain separate issues; do not edit `dist/` for the restart.

Host messages go out through [events.rs](src/events.rs), addressed to the main window. The address is not what keeps them there: Tauri delivers an event sent to one window to any page listener registered without a target, in whichever window it is, and that is the kind `listen` on the global object registers. Only the capability does, by granting event listening to the main window alone. Do not grant `core:event:allow-listen` to another window unless that window may read every host message; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) pins the capability's exact permissions and windows for this reason.

Run `npm run dev:app` to start the application from the bundled files, which is the path a release build uses and the one the security policy applies to. Plain `cargo tauri dev` also works: the Tauri CLI then serves `ui/` from a loopback address with its own reload script, which a development build accepts and a release build never does, and the content security policy is not applied on that path. Both need the Tauri CLI, installed once with `cargo install tauri-cli --locked`.

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root, then `npm run check`. The command's tests run on Tauri's windowless runtime and do not load the capability file; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) covers the transport against a fake window and reads the configuration, capability and shell files as text. Neither opens a window. A launched application is separate evidence, recorded per operating system: on macOS the tray menu cannot be opened by accessibility scripting, so hide, show and quit there are driven through the close button, the Dock icon and the application menu unless a person clicks the tray.

When wiring authentication, follow the core's [refresh recovery contract](../docs/auth-refresh-recovery.md). Keep the process alive until `AuthController::shutdown` returns on the host exit thread; it drains a running refresh through its credential-save attempt. Never call it reentrantly from a WorkOS API implementation or its change callback. The HTTP implementation must retain its 20-second timeout per request; an operating system keychain prompt can delay a store operation. Session verification remains separate from saving the rotated credential.

## Restart runtime ownership

[The data directory resolver](src/data.rs) uses the OS data root and the separate `org.opencoven.open-sesame.restart-development` namespace until #59/#87 settle production identity. `OPEN_SESAME_DEV_CONFIG_DIR` selects an absolute disposable qualification directory. Relative paths, parent traversal and existing symlink aliases into legacy data are refused. Protected roots include the identifier folder, `Open Sesame` under the OS data root and the actual native `Library/Application Support/Open Sesame` root, controller receipts under `.local/share/Open Sesame` and `.local/share/Perch`, and legacy lower-case data/state roots, including absolute `XDG_DATA_HOME/open-sesame`. The host supplies OS home/data roots; a relative legacy XDG data root is refused because its installed-data location cannot be established safely. Do not derive restart SQLite storage from the colliding bundle identifier or migrate installed Swift data. Opening runs on a background thread; pending storage requests return a still-opening sentence. Core accepts the result once, retains an opening failure as a plain storage error while other features remain available, and refuses late results after Quit. Shutdown drops an initialized SQLite connection. An opening thread blocked in an uninterruptible filesystem call is not joined on the UI thread and ends with the application process; no child process belongs to it. Case variants of the installed namespace are conservatively refused on macOS and Windows.

[Startup](src/startup.rs) owns one background login-shell capture. Requests may read the inherited snapshot while it is pending; no UI code may call the blocking `StartupEnv::get`. Quit cancels and joins capture before shutting down Core. The process runner must remain the sole collector of its own children (#97): do not install a global SIGCHLD reaper, call `wait(-1)` or otherwise collect runner-owned child statuses from the host. Terminal panes own their separate children through the terminal subsystem.

The [windowless bridge audit](src/router.rs) calls every admitted method with safe invalid input, exercising real handlers without opening dialogs or touching the clipboard. No admitted method is pending: with no sign-in running in the audit, the auth actions reach the router's sign-in branch, which answers that sign-in has not started, and a method admitted ahead of its handler must be listed with its issue. Unknown-method replies fail the audit. This is routing evidence; the actual-app storage, desktop-launch discovery and first-paint checks remain separate native acceptance.

For local native qualification, a debug-only `OPEN_SESAME_SELFTEST` object with `kind: "runtime"`, `phase: "save"` or `"list"`, a disposable marker `text` and optional `delayMs` loads [runtime-selftest.js](../ui/dev/runtime-selftest.js). It uses the actual page bridge and displays the saved/listed item or an error with `saved: false`. `OPEN_SESAME_RUNTIME_PROBE_DIR` opts into a fixed `runtime-fixture` lookup receipt from the actual AppState startup snapshot and Core override reader; it writes no environment values and starts no provider CLI. Probe work is queued on the blocking pool and never awaited by page-load or bridge callbacks. Each receipt preserves the observed event, process ID, sequence and environment source; per-observation files are retained, and an older completion cannot replace a newer latest receipt. These hooks neither add a renderer command nor run in a release build. Keep qualification folders outside protected user document locations and preserve the exact candidate identity and original failed attempts.
