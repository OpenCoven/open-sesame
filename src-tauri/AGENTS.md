# Tauri shell and new UI shell for the desktop restart

[open-sesame](src/lib.rs) is the Tauri 2 application of the restart in [epic #58](https://github.com/OpenCoven/open-sesame/issues/58): one window, a tray icon and one command. It is not shipped; the Swift host and Python bridge under [desktop](../desktop/AGENTS.md) remain the running application until the cutover. Read the root [instructions](../AGENTS.md) and the [core's instructions](../crates/AGENTS.md) first; the ownership, evidence, publication and prose rules there apply here.

The window label is not an isolation boundary. Any script in the main document can call the bridge, so the main window loads only this application's own files and no third-party script may ever be loaded there. That rule is held in four places, and a change that loosens one needs a reviewed reason: the content security policy in [tauri.conf.json](tauri.conf.json) admits only bundled script; [the capability](capabilities/default.json) grants the main window alone and names no remote page; [window.rs](src/window.rs) refuses navigation away from the application's pages and refuses new windows; and [router.rs](src/router.rs) drops a request from any other window or page before the gate is even asked.

[bridge_request](src/router.rs) is the only command. Do not add a second one: a new feature is a method on the wire protocol, admitted in the core's gate by the change that ports its handler. The command runs [gate::dispatch](../crates/core/src/gate.rs) first and then routes the allowed request to sign-in, to the window methods in [window.rs](src/window.rs), or to [Core::handle](../crates/core/src/handler.rs). [build.rs](build.rs) declares the command so that Tauri refuses it for any window the capability does not name. For a Windows build it also has the linker embed the application manifest in everything the package links and leaves Tauri's own copy out: Tauri's copy reaches the application binary only, and the library's test program does not start without one.

The main window is created in Rust in [window.rs](src/window.rs), not in the configuration, so the initialisation script sets `window.__OPEN_SESAME_NATIVE__` and `window.__OPEN_SESAME_VERSION__` before any page script runs. Closing the window hides it and keeps the page alive; the page must not load again when the window is shown. Quit is the tray's explicit action, and every way out ends in `RunEvent::Exit` in [lib.rs](src/lib.rs), which shuts the core down. The [tray](src/tray.rs) menu works everywhere; Tauri's tray emits no click events on Linux, so nothing may depend on a click there.

Summon is [summon.rs](src/summon.rs), from [#71](https://github.com/OpenCoven/open-sesame/issues/71): the ways to make the window appear from anywhere. The baseline works on every system: the tray menu, launching the application again, and `open-sesame --toggle`. `tauri-plugin-single-instance` must stay the first plugin registered in [lib.rs](src/lib.rs), so a second process hands its arguments to the running one and exits before it creates a window; without a D-Bus session bus on Linux the plugin does nothing and a second launch is a second application. On macOS, Windows and X11 a global shortcut toggles the window. It is registered from Rust through `tauri-plugin-global-shortcut`, and the capability grants the page none of that plugin's commands: the page asks through `summon.status`, `summon.setShortcut`, `summon.setHideOnBlur` and `summon.hold`, which are in the gate like any other method. A refused registration is kept and returned, never swallowed, and a refused change puts the previous shortcut back. macOS accepts a shortcut another application already holds, so a conflict cannot be detected there; X11 and Windows refuse it. The default, `Alt+Shift+Space`, was chosen because it is not what ChatGPT, Gemini, Raycast, Alfred or the Swift host use; changing it is the owner's call.

On Wayland an application cannot grab a key. [summon::session](src/summon.rs) decides the kind of session once, nothing is registered, the window is not positioned, `window.keepOpen` answers with the gate's not-on-this-system sentence, and the page names the command to bind in the desktop's own keyboard settings. Do not add a call that moves the window or forces it on top without a check for the session. The GlobalShortcuts portal is not used yet; [#108](https://github.com/OpenCoven/open-sesame/issues/108) owns it.

On macOS [panel.rs](src/panel.rs) turns the window into a panel with `tauri-nspanel`, so it takes the keyboard without activating the application and can appear on the Space in front, a full-screen one included. The panel crate's calls go straight to AppKit, which ends the process when a window is ordered from another thread; Tauri's own window calls are dispatched for you and these are not, so every one outside `setup` goes through `run_on_main_thread`. On Windows a left click on the tray icon places the window against the icon inside the screen's work area ([summon::popover_position](src/summon.rs)) and a right click opens the menu; elsewhere a click only opens the menu.

Hide-on-blur is a setting that is off unless the person turns it on. A feature that takes the focus away on purpose must take [summon::hold](src/summon.rs) first and keep the value until it is done: a native dialog, a browser sign-in. The page reports a drag with `summon.hold`, and a pinned window stays. The shortcut and this setting are kept in memory only: the folder Tauri derives is still the installed Swift app's, and where the restart keeps its data is [#105](https://github.com/OpenCoven/open-sesame/issues/105)'s question. A development build keeps them in the folder named by `OPEN_SESAME_DEV_CONFIG_DIR`, which a launched-app check uses so that it never writes into a person's home folder.

Sign-in is [auth.rs](src/auth.rs), from [#72](https://github.com/OpenCoven/open-sesame/issues/72): it gives the core's sign-in logic ([crates/core/src/auth](../crates/core/src/auth/mod.rs)) the network calls, the saved credential, a browser and the callback. It is an account control and not a door, as decided in [#60](https://github.com/OpenCoven/open-sesame/issues/60): the window opens in the shell, no method in the gate needs a session, and a refresh that cannot reach the server is tried again later without locking anything. Do not make a local feature wait for a session. The browser is opened from Rust only, through the opener crate's function, and only for an address on the WorkOS API origin ([auth::may_open](src/auth.rs)); the opener plugin is not registered and the page is granted neither it nor the deep-link plugin, so the page cannot open an address, register a scheme or read a link. The page learns the status from `auth.status` and from the `auth.changed` host message, which carry no address, code or credential.

The callback arrives through `tauri-plugin-deep-link` on the `opensesame` scheme named in [tauri.conf.json](tauri.conf.json). On macOS the system hands it to the running application; on Windows and Linux it starts a second process, and the single-instance plugin's `deep-link` feature passes it to the running one before that process exits, which is one more reason the plugin stays first. A callback is given to the core exactly as it arrived, and the core ignores one that does not carry the pending `state`, so a link sent by another program changes nothing. In a development build on Windows and Linux the scheme is registered at start for that run; on macOS only an installed bundle owns a scheme, so a development build there never receives a callback, and a bundle must not be built or launched on a machine where the installed Swift app owns the scheme until [#87](https://github.com/OpenCoven/open-sesame/issues/87) settles the identifier.

The refresh token is kept only by the system: Keychain, Windows Credential Manager or the Secret Service, through the `keyring` crate, under a service name that differs from the installed Swift app's because a refresh token is replaced each time it is used. On Linux with no Secret Service, sign-in is refused before the browser opens with a sentence that says what to install. Nothing in [auth.rs](src/auth.rs) may print or log: an address carries the `state` and an answer carries tokens. The signed-out flag, which matters only when a credential could not be deleted, is kept in memory in a release build for the reason the summon settings are ([#105](https://github.com/OpenCoven/open-sesame/issues/105)). A real sign-in needs a person and an account; the tests use a stand-in server on a loopback port and never contact WorkOS.

The new UI shell is [ui/](../ui/index.html), chosen in [#61](https://github.com/OpenCoven/open-sesame/issues/61) in place of carrying `dist/` over. It is framework-free ES modules with relative imports, no build step and no npm runtime dependency, and it shares no global between modules. [bridge.js](../ui/bridge.js) is the transport: it uses the global `window.__TAURI__` object, sends `{requestId, method, params}` through the command and hands host events to subscribers. Views, the widget manifest and lazy loading belong to [#76](https://github.com/OpenCoven/open-sesame/issues/76); do not edit `dist/` for the restart.

Host messages go out through [events.rs](src/events.rs), addressed to the main window. The address is not what keeps them there: Tauri delivers an event sent to one window to any page listener registered without a target, in whichever window it is, and that is the kind `listen` on the global object registers. Only the capability does, by granting event listening to the main window alone. Do not grant `core:event:allow-listen` to another window unless that window may read every host message; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) pins the capability's exact permissions and windows for this reason.

Run `npm run dev:app` to start the application from the bundled files, which is the path a release build uses and the one the security policy applies to. Plain `cargo tauri dev` also works: the Tauri CLI then serves `ui/` from a loopback address with its own reload script, which a development build accepts and a release build never does, and the content security policy is not applied on that path. Both need the Tauri CLI, installed once with `cargo install tauri-cli --locked`.

Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root, then `npm run check`. The command's tests run on Tauri's windowless runtime and do not load the capability file; [check-tauri-bridge.mjs](../scripts/check-tauri-bridge.mjs) covers the transport against a fake window and reads the configuration, capability and shell files as text. Neither opens a window. A launched application is separate evidence, recorded per operating system: on macOS the tray menu cannot be opened by accessibility scripting, so hide, show and quit there are driven through the close button, the Dock icon and the application menu unless a person clicks the tray.
